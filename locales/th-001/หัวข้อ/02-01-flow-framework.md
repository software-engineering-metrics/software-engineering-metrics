# 2.1 Flow Framework

## ภาพรวมและแรงจูงใจ

**Flow Framework** เป็นโมเดลเชิงการจัดการและโครงสร้างที่ Mik Kersten สร้างขึ้น
และเผยแพร่ในหนังสือ *Project to Product* ปี 2018
กรอบนี้มีไว้ตอบคำถามที่ตัวชี้วัดของสายพานล้วน ๆ ตอบไม่ได้
คือไม่ใช่แค่ว่าโค้ดเคลื่อนจาก commit ไปสู่ production ได้เร็วและปลอดภัยเพียงใด
แต่คือคุณค่าชนิดใดกำลังไหลผ่านสายพานอยู่
และส่วนผสมนั้นสะท้อนกลยุทธ์ที่แท้จริงของธุรกิจหรือไม่
กรอบนี้มองการส่งมอบซอฟต์แวร์เป็น
**[สายธารคุณค่า (value stream)](https://en.wikipedia.org/wiki/Value_stream)**
คือลำดับกิจกรรมแบบต้นทางถึงปลายทางที่เปลี่ยนไอเดียให้เป็นคุณค่าที่ลูกค้าได้รับ
โดยยืมตรง ๆ มาจากธรรมเนียมการทำแผนผังสายธารคุณค่าของการผลิตแบบลีน

หนังสือเล่มนี้ใช้ Flow Framework เป็นโครงสร้างหลักของส่วนที่ 2
หัวข้อ 2.2 แนะนำ flow item ทั้งสี่ประเภท
หัวข้อ 2.3 และ 2.4 แนะนำตัวชี้วัด flow ทั้งห้า
หัวข้อ 2.8 ไล่ตัวชี้วัดเหล่านั้นย้อนกลับไปถึงต้นกำเนิดในการทำแผนผังสายธารคุณค่าแบบลีนคลาสสิก
และหัวข้อ 2.10 ครอบคลุมตัวชี้วัด DORA ในฐานะกรอบอ้างอิงที่แคบกว่าและเน้นสายพาน
ซึ่งส่วนนี้ไม่ได้ใช้เป็นตัวนำอีกต่อไป
นี่เป็นการเลือกอย่างตั้งใจ ไม่ใช่การปัดงานวิจัยของ DORA ทิ้ง
DORA วัด throughput และเสถียรภาพของระบบด้วยความเข้มงวดทางสถิติจริง
แต่เงียบในเรื่องที่ผู้นำธุรกิจใส่ใจที่สุด
คือจากทุกสิ่งที่องค์กรวิศวกรรมส่งมอบในไตรมาสนี้
เป็นคุณค่าใหม่สำหรับลูกค้าเท่าไร
และถูกกลืนไปเงียบ ๆ กับการแก้ข้อบกพร่อง การจัดการความเสี่ยง หรือการใช้หนี้เท่าไร
Flow Framework มีขึ้นเพื่อทำให้ส่วนผสมนั้นมองเห็นได้โดยเฉพาะ

สำหรับทีมขนาดใหญ่ ความแตกต่างนี้ไม่ใช่เรื่องวิชาการ
องค์กรแพลตฟอร์มที่ดูแลสายธารคุณค่าหลายสิบสายอาจมีตัวเลข DORA ยอดเยี่ยม
คือ deploy เร็ว บ่อย และเสถียร
ขณะที่ผลผลิตจริงของผลิตภัณฑ์ค่อย ๆ เอียงไปเป็นงานบำรุงรักษาเกือบล้วน
รูปแบบที่มองไม่เห็นเลยบนแดชบอร์ดที่วัดแต่กลไกของสายพาน
องค์กรขนาดใหญ่และหน่วยงานภาครัฐซึ่งต้องชี้แจงการลงทุนด้านวิศวกรรมต่อผู้มีส่วนได้ส่วนเสียที่คิดเป็นภาษาธุรกิจ
ไม่ใช่ภาษาสายพาน ต้องการศัพท์ที่เชื่อมกิจกรรมการส่งมอบเข้ากับเจตนาเชิงกลยุทธ์
กรอบนี้ให้สิ่งนั้น

## หลักการสำคัญ

- **หน่วยของการวัดคือสายธารคุณค่า ไม่ใช่ทีมหรือสายพาน**
  สายธารครอบคลุมตั้งแต่ความต้องการของลูกค้าหรือธุรกิจไปจนถึงผลลัพธ์ที่ส่งมอบ
  ข้ามขอบเขตทีมทุกแห่งที่งานนั้นข้ามจริง
- **Flow item ทำให้มองเห็น "อะไร" ไม่ใช่แค่ "เร็วแค่ไหน"**
  สี่ประเภทของหัวข้อ 2.2 คือ ฟีเจอร์ ข้อบกพร่อง ความเสี่ยง และหนี้
  เปลี่ยนการตัดสินใจจัดลำดับความสำคัญที่ซ่อนอยู่ให้เป็นการตัดสินใจที่ชัดเจนและวัดได้
- **การจัดสรรกำลังคนข้าม flow item เป็นแบบผลรวมเป็นศูนย์**
  กำลังคนที่ใช้กับ item ประเภทหนึ่งมากขึ้น แปลว่าเหลือให้ประเภทอื่นน้อยลง
  กรอบนี้ทำให้ข้อแลกเปลี่ยนนั้นมองเห็นได้แทนที่จะปล่อยไว้ในที่ลับตา
- **ตัวชี้วัด flow ทั้งห้าตอบคำถามทางธุรกิจ ไม่ใช่แค่คำถามทางวิศวกรรม**
  ออกแบบมาให้นำเสนอต่อผู้มีส่วนได้ส่วนเสียที่ไม่ใช่เทคนิค
  ไม่ใช่เก็บไว้ในทีมวิศวกรรม
- **การบริหารสายธารคุณค่าควรทำอย่างต่อเนื่อง ไม่ใช่การทำแผนผังครั้งเดียวจบ**
  แผนผังสายธารคุณค่าแบบนิ่งจะล้าสมัย
  กรอบนี้สร้างมาให้ติดตั้งเครื่องมือวัดจากเครื่องมือที่ทีมใช้อยู่แล้ว

## ข้อเสนอแนะ

### ทำแผนผังสายธารคุณค่าก่อนติดตั้งเครื่องมือวัดใด ๆ

ก่อนนำตัวชี้วัด flow ใด ๆ มาใช้ ให้เดินตามเส้นทางจริงที่งานชิ้นหนึ่งผ่าน
ตั้งแต่ตอนที่ระบุความต้องการทางธุรกิจ จนถึงตอนที่ลูกค้าได้รับคุณค่า
โดยตั้งชื่อทุกขั้นตอนและทุกจุดส่งต่อระหว่างทีม
นี่คือการฝึก
[การทำแผนผังสายธารคุณค่า (value stream mapping)](https://en.wikipedia.org/wiki/Value_stream_mapping)
แบบคลาสสิกที่ดัดแปลงจากการผลิตแบบลีน
และการข้ามขั้นตอนนี้คือสาเหตุที่พบบ่อยที่สุดที่ทำให้การนำ Flow Framework มาใช้ได้ตัวเลขที่ไม่มีใครเชื่อถือ
ตัวชี้วัดที่คำนวณจากกระบวนการที่ไม่เคยตรวจสอบและเข้าใจกันแบบหลวม ๆ
แทบไม่เคยตรงกับสิ่งที่เกิดขึ้นจริง

### เชื่อมตัวชี้วัด flow เข้ากับเครื่องมือที่ทีมของคุณใช้อยู่แล้ว

Flow Framework สร้างมาเพื่อการบริหารสายธารคุณค่าแบบอัตโนมัติและต่อเนื่อง
ไม่ใช่การทำแผนผังด้วยมือเป็นระยะ
ให้ผนวกการติดตาม flow item เข้ากับเครื่องมือที่งานไหลผ่านอยู่แล้ว
เช่น Jira, Azure DevOps, GitHub
แทนที่จะสร้างระบบติดตามคู่ขนานที่ทีมต้องมาอัปเดตด้วยมือ
สถานะของ flow item ควรอัปเดตตัวเองเมื่อ ticket หรือ pull request เบื้องหลังเคลื่อนไป
เป็นวินัยแบบ "ใช้เครื่องมือวัดแทนการรายงานเอง" เดียวกับที่หัวข้อ 1.5 แนะนำสำหรับทุกตัวชี้วัดในหนังสือเล่มนี้

### นำเสนอ flow distribution ต่อผู้มีส่วนได้ส่วนเสียทางธุรกิจโดยตรง ไม่ใช่แค่ผู้นำฝ่ายวิศวกรรม

โอกาสที่พลาดกันมากที่สุดของกรอบนี้คือการมองมันเป็นเครื่องมือภายในของฝ่ายวิศวกรรม
Flow distribution คือสัดส่วนงานที่ไปกับฟีเจอร์เทียบกับข้อบกพร่อง ความเสี่ยง และหนี้ (หัวข้อ 2.3)
ออกแบบมาโดยเฉพาะให้เป็นบทสนทนากับผู้นำฝั่งผลิตภัณฑ์และธุรกิจ
เพราะมันทำให้การตัดสินใจจัดลำดับความสำคัญที่ซ่อนอยู่
คือกำลังคนเท่าไรไปกับคุณค่าใหม่ เทียบกับการประคองระบบให้ไฟยังติด
กลายเป็นเรื่องที่ชัดเจนและต่อรองได้ แทนที่จะถูกสมมติไปเอง

### ปฏิบัติต่อ flow item ทั้งสี่ประเภทเป็นอนุกรมวิธานจริง ไม่ใช่พิธีกรรม

กำหนดให้งานทุกชิ้นถูกจำแนกเป็น flow item ประเภทใดประเภทหนึ่งในสี่ประเภทเพียงประเภทเดียวตั้งแต่ตอนรับงานเข้า
ไม่ใช่ย้อนหลัง
การจำแนกที่ทำทีหลัง หรือทำอย่างหละหลวมเพราะ "มันก็เกือบเป็นฟีเจอร์แหละ"
กัดกร่อนคุณค่าทั้งหมดของอนุกรมวิธาน
เพราะจุดประสงค์ทั้งหมดคือบันทึกที่ซื่อสัตย์และสม่ำเสมอว่ากำลังคนไปอยู่ที่ใดจริง ๆ

### ทบทวนแผนผังสายธารคุณค่าเมื่อองค์กรเปลี่ยน ไม่ใช่ตามตารางเวลาตายตัว

แผนผังสายธารคุณค่าล้าสมัยทันทีที่ขอบเขตทีม เครื่องมือ หรือตัวผลิตภัณฑ์เปลี่ยนไปอย่างมีนัยสำคัญ
ไม่ใช่ตามรอบรายปีที่กำหนดขึ้นเอง
ให้ถือว่าการปรับโครงสร้างองค์กร การย้ายเครื่องมือครั้งใหญ่ หรือการเปลี่ยนทิศทางผลิตภัณฑ์อย่างมีนัยสำคัญ
เป็นตัวกระตุ้นให้เดินสำรวจสายธารคุณค่าใหม่
เพราะตัวชี้วัด flow ที่คำนวณจากแผนผังที่ล้าสมัยกำลังวัดสิ่งที่ผิดอยู่เงียบ ๆ

## ข้อแลกเปลี่ยน: ข้อดีและข้อเสีย

| แนวทาง | ข้อดี | ข้อเสีย |
| --- | --- | --- |
| ใช้ตัวชี้วัดสายพานอย่างเดียว (DORA, หัวข้อ 2.10) | เรียบง่าย ผ่านการพิสูจน์ดี ติดตั้งเครื่องมือวัดถูกจากข้อมูล CI/CD ที่มีอยู่ | เงียบเรื่องว่ากำลังส่งมอบคุณค่าชนิดใด |
| นำ Flow Framework มาใช้เต็มรูปแบบ | เชื่อมการส่งมอบเข้ากับกลยุทธ์ธุรกิจ ทำให้ส่วนผสมของคุณค่ามองเห็นและต่อรองได้ | ต้องมีแผนผังสายธารคุณค่าที่ซื่อสัตย์และวินัยการจำแนก flow item ที่สม่ำเสมอ |
| ทำแผนผังสายธารคุณค่าแบบนิ่งครั้งเดียว | ถูก ทำเป็นเวิร์กช็อปได้เร็ว | ล้าสมัยเร็ว ได้ภาพนิ่งหนึ่งภาพ ไม่ใช่ตัวชี้วัดที่มีชีวิต |
| บริหารสายธารคุณค่าต่อเนื่องแบบผนวกกับเครื่องมือ | ข้อมูลสดและทันสมัยเสมอ ขยายได้ข้ามหลายสายธาร | ต้องลงแรงผนวกเครื่องมือจริงจังล่วงหน้า |

ความตึงเครียดหลักคือ **ความอ่านออกของธุรกิจเทียบกับแรงที่ต้องใช้ติดตั้งเครื่องมือวัด**
ตัวชี้วัดสายพานถูกเพราะสายพานสร้างข้อมูลอยู่แล้ว
ส่วนตัวชี้วัดสายธารคุณค่าต้องมีแผนผังที่ซื่อสัตย์ของกระบวนการทั้งหมด
และนิสัยจำแนกประเภทตอนรับงานอย่างมีวินัย ซึ่งตัวชี้วัดสายพานไม่เคยเรียกร้อง
วิธีคลายความตึงเครียดคือเริ่มจากสายธารเดียว ไม่ใช่ทั้งองค์กรพร้อมกัน
ทำแผนผังให้ถูกต้องก่อน แล้วค่อยผนวกการติดตาม flow item เข้ากับเครื่องมือที่มีอยู่
แทนที่จะพยายามเปิดใช้ทีเดียวทั่วทุกทีมพร้อมกัน

## คำถามเพื่อหารือกับทีมของคุณ

1. **ตอนนี้เราวาดแผนผังสายธารคุณค่าที่ถูกต้องของผลิตภัณฑ์สำคัญที่สุดได้หรือไม่
   หรือจะต้องเดาจุดส่งต่อหลายจุด?**
   องค์กรส่วนใหญ่ไม่เคยเดินเส้นทางนี้ตั้งแต่ต้นจนจบจริง ๆ
   ลองทำแบบฝึกหัดนี้อย่างซื่อสัตย์ และจดทุกจุดที่กลุ่มเห็นไม่ตรงกันว่าเกิดอะไรขึ้นจริง
   เพราะความเห็นไม่ตรงกันนั้นเองคือผลวินิจฉัย

2. **ถ้าเราจำแนกทุกอย่างที่ทีมส่งมอบเมื่อไตรมาสที่แล้วเป็นฟีเจอร์ ข้อบกพร่อง ความเสี่ยง และหนี้
   ผลลัพธ์จะทำให้ผู้นำฝั่งผลิตภัณฑ์ประหลาดใจหรือไม่?**
   ทีมส่วนใหญ่ไม่เคยแยกสัดส่วนนี้อย่างชัดเจน
   และคำตอบมักเผยภาระการบำรุงรักษาหรือปัญหาหนี้ที่เดิมมองไม่เห็นในยอด "story point ที่ส่งมอบ" แบบง่าย ๆ

3. **เรามีวิธีติดตาม flow item ที่ผนวกกับเครื่องมือจริงหรือไม่
   หรือต้องให้ใครสักคนมาจำแนกและจำแนกงานใหม่ด้วยมือ?**
   ระบบแบบทำมือเสื่อมเร็วภายใต้ภาระงานจริง ระบบที่ผนวกกับเครื่องมือไม่เป็นเช่นนั้น
   ประเมินอย่างซื่อสัตย์ว่าคุณพร้อมรักษาแบบไหนได้จริง

4. **แผนผังสายธารคุณค่าของเราเปลี่ยนครั้งล่าสุดเมื่อใด และเราปรับตัวชี้วัดให้สะท้อนการเปลี่ยนนั้นแล้วหรือยัง?**
   การปรับโครงสร้างองค์กรและการย้ายเครื่องมือทำให้แผนผังสายธารคุณค่าใช้ไม่ได้โดยไม่มีเสียงเตือน
   และมีองค์กรไม่กี่แห่งที่จำได้ว่าต้องกลับมาทบทวน

5. **ตัวชี้วัด flow ของเราเคยถูกนำเสนอต่อผู้มีส่วนได้ส่วนเสียฝ่ายธุรกิจหรือผลิตภัณฑ์โดยตรงหรือไม่
   หรืออยู่แต่ในฝ่ายวิศวกรรม?**
   ข้อได้เปรียบใหญ่ที่สุดของกรอบนี้เหนือตัวชี้วัดสายพานอย่างเดียวคือบทสนทนานี้
   และการข้ามมันไปทำให้เสียคุณค่าส่วนใหญ่ของกรอบ

6. **ต้องทำอย่างไรจึงจะมีคนเล่นแร่แปรธาตุการจำแนก flow item ของเราได้
   โดยไม่ทำอะไรไม่ซื่อสัตย์บนกระดาษเลย?**
   ลองไล่ดูว่าทีมที่ถูกกดดันเรื่องการส่งมอบอาจแอบเปลี่ยนป้ายงานหนี้หรืองานความเสี่ยงให้เป็นฟีเจอร์
   เพื่อให้ดูทำงานได้มากขึ้นอย่างไร และคุยกันว่าตอนนี้คุณจะสังเกตเห็นหรือไม่

## มุมมองตามภาคส่วน

**สตาร์ทอัป** แผนผังสายธารคุณค่าเต็มรูปแบบมักเกินจำเป็นสำหรับทีมห้าคนที่ทุกคนรู้กระบวนการทั้งหมดขึ้นใจอยู่แล้ว
นิสัยที่มีประโยชน์ในระดับนี้คือเอ่ยชื่อ flow item ทั้งสี่ประเภทออกเสียงในการคุยวางแผน
เพื่อให้งานหนี้และงานความเสี่ยงไม่หายไปจากสายตาเงียบ ๆ ทันทีที่เดดไลน์ฟีเจอร์ใกล้เข้ามา

**ธุรกิจขนาดเล็ก** ใช้การจำแนก flow item ภายในเครื่องมือติดตามงานเบา ๆ ที่คุณมีอยู่แล้ว
เช่นคอลัมน์ที่ติดป้ายหรือฟิลด์กำหนดเอง แทนที่จะใช้ผลิตภัณฑ์บริหารสายธารคุณค่าโดยเฉพาะ
วินัยของการจำแนกอย่างสม่ำเสมอสำคัญกว่าความซับซ้อนของเครื่องมือเบื้องหลังมาก

**องค์กรขนาดใหญ่** ที่นี่คือที่ที่กรอบนี้คุ้มค่าตัวมันเอง
เพราะองค์กรใหญ่ที่ดูแลสายธารคุณค่าหลายสิบสายในหลายสายผลิตภัณฑ์
ไม่มีวิธีอื่นที่เชื่อถือได้ในการเห็นภาพรวมในที่เดียวว่ากำลังคนด้านวิศวกรรมถูกจัดสรรไปกับฟีเจอร์ ข้อบกพร่อง ความเสี่ยง และหนี้อย่างไร
จงลงทุนกับการผนวกเครื่องมือ ทางเลือกแบบทำมือไม่รอดเมื่อเจอขนาดจริง

**ภาครัฐ** Flow distribution ให้องค์กรวิศวกรรมภาครัฐมีคำตอบที่ปกป้องได้และธุรกิจอ่านเข้าใจ
เมื่อถูกถามว่า "ทำไมฟังก์ชันใหม่ถึงออกไม่มากขึ้น"
ในกรณีที่คำตอบจริงคือกำลังคนสัดส่วนที่เพิ่มขึ้นไปกับการแก้ไขด้านความปลอดภัยหรือหนี้ของระบบเดิม
การทำให้ข้อแลกเปลี่ยนนั้นมองเห็นและชัดเจน แทนที่จะรับแรงกดดันไว้เงียบ ๆ
มักเป็นสิ่งที่มีประโยชน์ที่สุดอย่างเดียวที่กรอบนี้มอบให้ผู้นำด้านเทคโนโลยีภาครัฐ

## ตัวอย่าง

**องค์กรขนาดใหญ่** องค์กรแพลตฟอร์มเคลมของบริษัทประกันขนาดใหญ่แห่งหนึ่งเชื่อว่าตนส่งมอบฟีเจอร์ใหม่เป็นหลัก
โดยดูจากรายงาน velocity ของสปรินต์
การทำแผนผังสายธารคุณค่าและจำแนก flow item ครั้งแรกเผยว่า
งานหนี้และงานความเสี่ยง ซึ่งส่วนใหญ่เป็นหนี้ทางเทคนิคที่ไม่มีเอกสารจากระบบแกนกลางอายุสิบปี
ใช้กำลังคนด้านวิศวกรรมทั้งหมดไปเกือบครึ่ง
ข้อเท็จจริงที่รายงานก่อนหน้าไม่เคยเปิดเผย
เพราะงานนั้นถูกรวมเป็น "งานวิศวกรรม" ทั่วไปมาตลอด
การนำเสนอสัดส่วนนี้ต่อคณะกรรมการบริหารทำให้ได้งบลดหนี้โดยเฉพาะเป็นครั้งแรกในประวัติศาสตร์ของแพลตฟอร์ม
แทนที่งานหนี้จะต้องแย่งชิงกับคำขอฟีเจอร์ทุกรายการอย่างเงียบ ๆ ต่อไป

**ภาครัฐ** ฝ่ายบริการดิจิทัลของหน่วยงานภาษีแห่งชาติใช้การทำแผนผังสายธารคุณค่า
เพื่อวินิจฉัยว่าทำไมฟีเจอร์เรือธงที่ประชาชนใช้จึง "กำลังดำเนินการ" มานานกว่าหนึ่งปี
ทั้งที่สปรินต์เสร็จสม่ำเสมอ
แผนผังเผยว่าสายธารคุณค่าจริงครอบคลุมห้าทีม มีจุดส่งต่อสามจุดที่ผังองค์กรไม่ได้สะท้อน
และการจำแนก flow item แสดงว่าเวลาวิศวกรรมจริงของฟีเจอร์เป็นเพียงเศษเสี้ยวเล็ก ๆ ของ flow time ทั้งหมด
ที่เหลือหมดไปกับความล่าช้าตอนส่งต่อระหว่างทีม
ซึ่งตัวชี้วัดของทีมใดทีมหนึ่งเองมองไม่เห็น
ฝ่ายจึงปรับโครงสร้างตามสายธารคุณค่าแทนผังองค์กรสำหรับสายผลิตภัณฑ์นั้น
ลด flow time ลงอย่างมากภายในสองไตรมาส

## เหตุผลทางธุรกิจ: แรงจูงใจ ROI และ TCO

ผลตอบแทนจากการนำ Flow Framework มาใช้คือคำตอบที่ปกป้องได้และธุรกิจอ่านเข้าใจ
สำหรับคำถามที่ตัวชี้วัดสายพานตอบไม่ได้ คือกำลังคนด้านวิศวกรรมถูกจัดสรรตรงกับที่ผู้บริหารเชื่อหรือไม่
ตัวอย่างบริษัทประกันข้างต้นที่พบว่ากำลังคนเกือบครึ่งไปกับงานหนี้ที่เดิมมองไม่เห็น
เป็นรูปแบบที่พบบ่อยเมื่อองค์กรจำแนกงานของตนอย่างซื่อสัตย์จริง
และการมองเห็นนั้นมักปลดล็อกการลงทุนที่คำขอลอย ๆ ว่า "เราต้องการเวลาเพิ่มสำหรับหนี้ทางเทคนิค" ไม่เคยทำได้

ต้นทุนรวมในการเป็นเจ้าของกระจุกอยู่สองที่
คือการทำแผนผังสายธารคุณค่าครั้งแรก ซึ่งต้องใช้เวลาอำนวยการจริงจึงจะทำได้อย่างซื่อสัตย์
และการผนวกเครื่องมือที่จำเป็นเพื่อให้ข้อมูล flow item ทันสมัยโดยไม่ต้องดูแลด้วยมือ
ต้นทุนทั้งสองเป็นครั้งเดียวหรือดูแลน้อยเมื่อทำดี
ทำให้กรอบนี้ถูกกว่ามากที่จะรักษาไว้เมื่อเทียบกับตอนนำมาใช้

## แอนตี้แพตเทิร์นและข้อผิดพลาด

- **มองการทำแผนผังสายธารคุณค่าเป็นเวิร์กช็อปครั้งเดียวและไม่กลับมาทบทวน:**
  แผนผังล้าสมัยทันทีที่องค์กรเปลี่ยน และตัวชี้วัดที่คำนวณจากแผนผังที่ล้าสมัยวัดสิ่งที่ผิด
- **สร้างระบบติดตาม flow item คู่ขนานที่ดูแลด้วยมือ:**
  เสื่อมเร็วภายใต้ภาระงานจริง ให้ผนวกเข้ากับเครื่องมือที่มีอยู่แทน
- **จำแนก flow item ย้อนหลังแทนที่จะทำตอนรับงาน:**
  นี่คือ gaming vector ที่เป็นหัวใจของหัวข้อนี้
  ภายใต้แรงกดดันเรื่องการส่งมอบ ทีมอาจเปลี่ยนป้ายงานหนี้หรืองานความเสี่ยงให้เป็นฟีเจอร์ภายหลังอย่างเงียบ ๆ
  เพื่อให้ดูทำงานได้มากขึ้นในสายตาผู้มีส่วนได้ส่วนเสียที่เห็นแต่แผนภูมิ flow distribution
  โดยไม่มีใครตัดสินใจทำเช่นนั้นอย่างชัดเจนและเปิดเผยเลย
  guardrail คือกำหนดให้จำแนกตอนรับงานก่อนที่จะรู้ผลลัพธ์
  และสุ่มตรวจรายการที่จำแนกแล้วเป็นระยะเทียบกับสิ่งที่การเปลี่ยนแปลงเบื้องหลังทำจริง
  เป็นวินัยการตรวจสอบเดียวกับที่หัวข้อ 1.2 ขอให้ทำกับทุกตัวชี้วัดในหนังสือเล่มนี้
- **เก็บตัวชี้วัด flow ไว้ในฝ่ายวิศวกรรมเท่านั้น:**
  เสียข้อได้เปรียบหลักของกรอบ คือศัพท์ร่วมกับผู้มีส่วนได้ส่วนเสียฝ่ายธุรกิจ
- **ทำแผนผังองค์กรแทนที่จะทำแผนผังสายธารคุณค่าจริง:**
  ซ่อนจุดส่งต่อข้ามทีมซึ่งมักเป็นแหล่งความล่าช้าที่ใหญ่ที่สุด
- **นำกรอบไปใช้ทั้งองค์กรก่อนพิสูจน์กับสายธารคุณค่าเดียว:**
  เสี่ยงลงทุนก้อนใหญ่กับตัวชี้วัดที่ไม่มีใครเชื่อถือ
  เพราะแผนผังเบื้องหลังไม่เคยได้รับการยืนยันว่าถูกต้อง

## แบบจำลองวุฒิภาวะ

- **ระดับ 1 เริ่มต้น (Initiate):** ไม่มีแผนผังสายธารคุณค่า งานถูกติดตามเป็น ticket ทั่วไปโดยไม่มีการจำแนก flow item
- **ระดับ 2 พัฒนา (Develop):** ทำแผนผังสายธารคุณค่าหนึ่งสายแล้ว และจำแนก flow item แบบไม่เป็นทางการ
  แต่การติดตามทำด้วยมือและใช้ไม่สม่ำเสมอ
- **ระดับ 3 มาตรฐาน (Standardize):** การจำแนก flow item ผนวกกับเครื่องมือที่มีอยู่
  และใช้อย่างสม่ำเสมอตอนรับงานข้ามสายธารคุณค่าหลัก
- **ระดับ 4 บริหารจัดการ (Manage):** ทบทวน flow distribution กับผู้มีส่วนได้ส่วนเสียฝ่ายธุรกิจเป็นประจำ
  และดูแลแผนผังสายธารคุณค่าให้ทันสมัยอยู่เสมอเมื่อองค์กรเปลี่ยน
- **ระดับ 5 ประสาน (Orchestrate):** องค์กรจัดสรรการลงทุนด้านวิศวกรรมข้ามสายธารคุณค่าอย่างตั้งใจโดยใช้ข้อมูล flow
  และชี้ได้ถึงการตัดสินใจเชิงกลยุทธ์เฉพาะ เช่นงบลดหนี้หรือการปรับโครงสร้างทีม
  ที่เกิดขึ้นเพราะกรอบนี้ทำให้ข้อแลกเปลี่ยนที่เคยมองไม่เห็นกลายเป็นมองเห็น

## ประเด็นเพื่อการอภิปราย

1. วันนี้เราวาดแผนผังสายธารคุณค่าที่ถูกต้องของผลิตภัณฑ์เรือธงโดยไม่ต้องเดาได้หรือไม่?
2. การจำแนก flow item อย่างซื่อสัตย์จะเผยว่ากำลังคนของไตรมาสที่แล้วไปกับหนี้และความเสี่ยงกี่เปอร์เซ็นต์ เทียบกับฟีเจอร์?
3. ตัวชี้วัด flow ของเราไปถึงผู้มีส่วนได้ส่วนเสียฝ่ายธุรกิจหรือไม่ หรืออยู่แต่ในฝ่ายวิศวกรรม?
4. จุดส่งต่อข้ามทีมที่ใหญ่ที่สุดในสายธารคุณค่าของเราที่ผังองค์กรไม่ได้สะท้อนคืออะไร?

## ข้อสรุปสำคัญ

- **Flow Framework** จาก *Project to Product* ของ Mik Kersten วัดว่าคุณค่าชนิดใดไหลผ่านสายพานการส่งมอบ
  ไม่ใช่แค่ว่าสายพานเองวิ่งเร็วแค่ไหน
- **สายธารคุณค่า** ไม่ใช่ทีมหรือสายพาน คือหน่วยของการวัดของกรอบนี้
  และการทำแผนผังอย่างซื่อสัตย์มาก่อนการติดตั้งเครื่องมือวัดใด ๆ
- **การจำแนก flow item ตอนรับงาน ไม่ใช่ทำทีหลัง** คือ guardrail
  ต่อ gaming vector หลักของหัวข้อนี้ คือการเปลี่ยนป้ายงานหนี้หรืองานความเสี่ยงเป็นฟีเจอร์อย่างเงียบ ๆ
  เพื่อให้ดูทำงานได้มากขึ้น
- **เชื่อมตัวชี้วัด flow เข้ากับเครื่องมือที่มีอยู่** เช่น Jira, Azure DevOps, GitHub
  แทนที่จะใช้ระบบติดตามด้วยมือคู่ขนานที่ไม่รอดภาระงานจริง
- นำเสนอข้อมูล flow **ต่อผู้มีส่วนได้ส่วนเสียฝ่ายธุรกิจโดยตรง**
  บทสนทนานั้น ไม่ใช่แดชบอร์ดภายในของฝ่ายวิศวกรรม
  คือข้อได้เปรียบหลักของกรอบนี้เหนือตัวชี้วัดสายพานอย่างเดียว
