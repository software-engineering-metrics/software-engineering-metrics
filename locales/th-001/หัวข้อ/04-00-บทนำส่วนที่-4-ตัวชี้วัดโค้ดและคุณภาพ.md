# 4.0 บทนำส่วนที่ 4: ตัวชี้วัดโค้ดและคุณภาพ

ส่วนที่ 2 และ 3 วัดว่างานไหลไปอย่างไร และคนที่ทำงานนั้นเป็นอยู่อย่างไร ส่วนนี้หันมาดูตัวชิ้นงานเอง นั่นคือโค้ด และสิ่งที่ตัวชี้วัดบอกได้หรือบอกไม่ได้เกี่ยวกับคุณภาพของโค้ด ตัวชี้วัดคุณภาพโค้ดมีประวัติยาวนานที่สุดในบรรดาตระกูลตัวชี้วัดทั้งหมดในหนังสือเล่มนี้ cyclomatic complexity มีที่มาตั้งแต่ปี 1976 และประวัติการนำไปใช้ผิดวิธีก็ยาวนานไม่แพ้กัน ส่วนนี้จึงจริงจังกับประวัติศาสตร์นั้น ทุกหัวข้อจะบอกสัญญาณที่มีประโยชน์จริง และบอกวิธีที่มีการบันทึกไว้อย่างชัดเจนว่าสัญญาณนั้นถูกเล่นแร่แปรธาตุเมื่อกลายเป็นเป้าหมาย

เส้นเรื่องที่ร้อยหัวข้อทั้งหกเข้าด้วยกันคือ ไม่มีตัวชี้วัดโค้ดตัวเดียวที่จับคุณภาพได้ครบ และตัวที่ได้รับความนิยมสูงหลายตัวยังพาให้เข้าใจผิดอย่างจริงจังเมื่อไล่ตามมันโดยลำพัง เปอร์เซ็นต์ test coverage ที่สูงอยู่ร่วมกับเทสต์ที่ไม่ได้ตรวจสอบอะไรที่มีความหมายได้ คะแนนความซับซ้อนที่ต่ำอยู่ร่วมกับโค้ดที่ง่ายในทางเทคนิคแต่สับสนในเชิงแนวคิดได้ แต่ละหัวข้อในส่วนนี้จึงจับคู่ตัวชี้วัดหลักเข้ากับการตรวจสอบเสริมที่อุดจุดบอดเฉพาะของมัน ได้แก่ ความซับซ้อนคู่กับบริบทด้านความสามารถในการบำรุงรักษา coverage คู่กับ mutation testing churn คู่กับการวิเคราะห์ hotspot การวิเคราะห์เชิงสถิต (static analysis) คู่กับวิจารณญาณของมนุษย์ และหนี้ทางเทคนิคคู่กับการแก้ไขตามลำดับความสำคัญ แทนที่จะปล่อยให้เป็น backlog ที่โตขึ้นเรื่อย ๆ โดยไม่มีใครเหลียวแล

สำหรับทีมขนาดใหญ่ ตัวชี้วัดโค้ดและคุณภาพคือสิ่งที่ทำให้จัดการโค้ดเบสที่ใหญ่เกินกว่าคนคนเดียวจะเก็บไว้ในหัวได้ ทีมห้าคนพึ่งความรู้โดยปริยายที่ร่วมกันได้ว่าส่วนไหนของระบบเปราะบาง แต่องค์กรที่มีวิศวกรห้าร้อยคนและหลายสิบบริการต้องมีสัญญาณที่มีเครื่องมือวัดเพื่อหาความเปราะบางนั้นอย่างเป็นระบบ องค์กรขนาดใหญ่และหน่วยงานภาครัฐที่มักมีโค้ดเบสอายุเป็นทศวรรษมากกว่าเป็นปี พึ่งตัวชี้วัดในส่วนนี้เพื่อตัดสินว่างบบำรุงรักษาที่มีจำกัดควรลงตรงไหนจึงจะเกิดประโยชน์สูงสุด

## หัวข้อในส่วนนี้

- **4.1 ตัวชี้วัดความซับซ้อนของโค้ด:** cyclomatic complexity และตัวชี้วัดในตระกูลเดียวกัน สิ่งที่มันทำนายได้จริง และความเสี่ยงที่ถูกเล่นแร่แปรธาตุซึ่งมีการบันทึกไว้อย่างดี
- **4.2 test coverage และประสิทธิผลของเทสต์:** ทำไมเปอร์เซ็นต์ coverage เพียงตัวเดียวบอกอะไรได้น้อยกว่าที่ดูเหมือน และ mutation testing อุดช่องว่างนั้นได้อย่างไร
- **4.3 code churn และการวิเคราะห์ hotspot:** การหาส่วนเล็ก ๆ ของโค้ดเบสที่รับผิดชอบต่อข้อบกพร่องและต้นทุนการบำรุงรักษาเกินสัดส่วน
- **4.4 การวิเคราะห์เชิงสถิตและตัวชี้วัด code smell:** สัญญาณคุณภาพโค้ดแบบอัตโนมัติ คุณค่าที่แท้จริง และขีดจำกัดเมื่อเทียบกับวิจารณญาณของมนุษย์
- **4.5 การวัดหนี้ทางเทคนิค:** เปลี่ยนภาระที่มองไม่เห็นและถูกพูดถึงอย่างไม่เป็นทางการ ให้เป็นพอร์ตโฟลิโอที่มองเห็นได้ จัดลำดับความสำคัญได้ และบริหารได้
- **4.6 ตัวชี้วัดเอกสารและความรู้:** วัดว่าเอกสารช่วยได้จริงหรือไม่ ไม่ใช่แค่ว่ามีเอกสารอยู่หรือเปล่า

## หัวข้อเหล่านี้เกี่ยวข้องกันอย่างไร

หัวข้อทั้งหกนี้ไล่จากหน่วยเล็กที่สุดของโค้ดออกไปข้างนอก หัวข้อ 4.1 เริ่มที่ระดับฟังก์ชันหรือเมธอดเดียว หัวข้อ 4.2 ถามว่าเทสต์ตรวจสอบพฤติกรรมของหน่วยนั้นจริงหรือไม่ หัวข้อ 4.3 ขยายภาพออกเพื่อหาว่าไฟล์และโมดูลไหนทั่วทั้งโค้ดเบสควรได้รับความสนใจก่อน หัวข้อ 4.4 เพิ่มชั้นเครื่องมืออัตโนมัติที่สแกนทุกอย่างอย่างต่อเนื่อง หัวข้อ 4.5 รวมสิ่งที่พบจากสี่หัวข้อแรกเป็น backlog ที่จัดการและจัดลำดับได้ แทนที่จะเป็นความกังวลที่กระจัดกระจายและไม่มีใครแตะ และหัวข้อ 4.6 ปิดส่วนนี้ด้วยการวัดว่าความรู้ที่จำเป็นต่อการบำรุงรักษาทั้งหมดนี้อย่างปลอดภัยถูกบันทึกไว้และค้นหาเจอจริงหรือไม่

ส่วนนี้เชื่อมโดยตรงกลับไปยังตัวชี้วัดด้านเสถียรภาพในส่วนที่ 2 อัตราความล้มเหลวของการเปลี่ยนแปลง (หัวข้อ 2.10) ส่วนใหญ่เป็นผลที่ตามมาจากคุณภาพโค้ดซึ่งส่วนนี้วัดไว้ต้นน้ำ และเชื่อมไปข้างหน้ายังตัวชี้วัดผลิตภัณฑ์ในส่วนที่ 5 ด้วย เพราะข้อบกพร่องที่หลุดไปถึงผู้ใช้ (หัวข้อ 5.1) มักสืบย้อนไปถึง hotspot ด้านความซับซ้อนและช่องว่างของ coverage ที่ส่วนนี้สร้างขึ้นเพื่อให้เห็นก่อนที่มันจะไปถึง production
