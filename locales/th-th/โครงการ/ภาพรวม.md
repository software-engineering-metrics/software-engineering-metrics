# เกี่ยวกับโครงการนี้

เอกสารโครงการของหนังสือ: ประกอบกันอย่างไร build และตรวจสอบอย่างไร และแหล่งความจริงอยู่ที่ไหน
สำหรับตัวหนังสือเอง ดู[สารบัญ](../index.md)

## แผนที่ของโครงการ

- **หนังสือ:** เผยแพร่ในสี่ locale ภายใต้ `locales/` ดู
  [spec/locales.md](https://github.com/software-engineering-metrics/software-engineering-metrics/blob/main/spec/locales.md)
  locale นี้ คือ `en-gb-oxendict/topics/` (63 ไฟล์) `en-gb-oxendict/front-matter/`
  และภาคผนวกในส่วนที่ 9 เป็นต้นฉบับที่เขียนด้วยมือ ส่วน `en-001`
  `en-gb` และ `en-us` สร้างจากมัน
- **แหล่งความจริง:** `spec/` ที่ราก repository (ไม่ได้เผยแพร่บน
  เว็บไซต์) โครงสร้างกำหนดไว้ใน `spec/structure.md` กฎการเขียน
  อยู่ใน `spec/conventions.md` และการสะกดอยู่ใน `spec/oxford-spelling.md`
  ทุกอย่างอื่นถูกสร้างให้ตรงกับสิ่งเหล่านี้
- **เครื่องมือ:** `tools/localize.py` สร้างอีกสาม locale
  `tools/gen_nav.py` สร้างการนำทาง `tests/validate.py` บังคับใช้
  ข้อกำหนด และ `justfile` เชื่อมทุกอย่างเข้าด้วยกัน
- **คู่มือสำหรับผู้มีส่วนร่วม:**
  [`AGENTS.md`](https://github.com/software-engineering-metrics/software-engineering-metrics/blob/main/AGENTS.md)
  ที่ราก repository และคู่มือใน[ส่วนการมีส่วนร่วม](../การมีส่วนร่วม/ภาพรวม.md)

## Build และตรวจสอบ

ชุดตรวจสอบรันบน Python 3 โดยไม่ต้องพึ่งอะไรอื่นและไม่ใช้เครือข่าย งานต่าง ๆ รันผ่าน [just](https://github.com/casey/just)

```sh
just test    # validate structure, style, links, and spec-vs-disk
just nav     # regenerate the generated navigation files
just check   # nav, then test
just stats   # topic and word counts
```

repository นี้เก็บเนื้อหาของหนังสือและข้อกำหนด ถูกแปลงเป็นเว็บไซต์โดย repository ที่แยกออกมา
[`software-engineering-metrics.github.io`](https://github.com/software-engineering-metrics/software-engineering-metrics.github.io)

## การพัฒนาที่ขับเคลื่อนด้วยข้อกำหนดทำงานอย่างไรที่นี่

ข้อกำหนดมาก่อน `spec/structure.md` บอกว่ามีหัวข้อใดบ้างและให้เลขอย่างไร
`spec/conventions.md` บอกว่าต้องเขียนอย่างไร หัวข้อถูกเขียนให้เป็นไปตามทั้งสองอย่าง
`tools/gen_nav.py` สร้างการนำทางจากหัวข้อ และ `tests/validate.py` ตรวจผลลัพธ์
กลับไปเทียบกับข้อกำหนด หากหัวข้อกับข้อกำหนดขัดกัน
การทดสอบจะไม่ผ่าน ซึ่งเป็นสัญญาณให้ปรับให้ตรงกันอีกครั้ง

วิธีนี้กันความเบี่ยงเบน: การเปลี่ยนแปลงถือว่า "เสร็จ" ก็ต่อเมื่อข้อกำหนด หัวข้อ
การนำทางที่สร้าง และการทดสอบ ลงรอยกันทั้งหมด

## การตัดสินใจออกแบบที่ควรรู้

- **หัวข้อแบบแบนและให้เลขทศนิยม** ไฟล์คือ
  `locales/<locale>/topics/PP-CC-slug.md` slug เดียวกันในทุก locale
  ส่วนเป็นจำนวนเต็ม หัวข้อเป็นทศนิยม N.0 คือบทนำส่วน วิธีนี้ให้ตัวระบุที่คงที่
  และให้เครื่องมือเรียงและจัดกลุ่มได้โดยไม่ต้องมีต้นไม้ไดเรกทอรี
- **หนึ่ง locale เขียนด้วยมือ อีกสามสร้างจากมัน** `en-gb-oxendict` ใช้การสะกดแบบ Oxford
  ซึ่งเป็นสไตล์ของหน่วยงานมาตรฐานระหว่างประเทศส่วนใหญ่ (ดู
  `spec/oxford-spelling.md`) ส่วน `en-001`, `en-gb` และ `en-us` สร้างจากมันโดยกลไก
  การแปลจึงไม่เบี่ยงจากต้นฉบับ
- **การนำทางที่สร้างอัตโนมัติ** สารบัญ หน้าเนื้อหา และดัชนีเรื่องถูกสร้างอัตโนมัติ
  จึงไม่เบี่ยงจากหัวข้อ
- **การทดสอบแบบออฟไลน์และไม่พึ่งแพ็กเกจ** ชุดตรวจสอบใช้เฉพาะไลบรารีมาตรฐาน
  จึงรันได้ทุกที่ รวมถึง CI และ pre-commit hook
- **การอ้างอิงข้ามเป็นข้อความธรรมดา** เนื้อความอ้างถึงหัวข้อด้วยเลขทศนิยม
  ("ดูหัวข้อ 2.1") ตามที่ข้อกำหนดกำหนด เว็บไซต์ที่เรนเดอร์
  รับผิดชอบแปลงการอ้างอิงเหล่านั้นเป็นลิงก์
- **ไม่มีเส้นประยาว ทั้งโดยกฎและโดยการทดสอบ** เป็นการเลือกสไตล์โดยตั้งใจ บังคับใช้
  เพื่อให้เป็นจริงต่อไปเมื่อหนังสือขยายตัว
- **ตระกูลตัวชี้วัดทุกตระกูลระบุ gaming vector ของตัวเอง** นี่เป็นกฎข้อเดียว
  ในเทมเพลตที่ไม่มีเทียบเท่าในโครงการพี่น้อง
  `software-engineering-guide` มันมีอยู่เพราะเรื่องทั้งหมดของหนังสือนี้คือการวัด
  ความเสี่ยงของการวัดเองจึงต้องเป็นเรื่องหลัก ไม่ใช่เรื่องแฝง
