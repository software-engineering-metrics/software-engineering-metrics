# 2.4 Flow time และ flow load

## ภาพรวมและแรงจูงใจ

**Flow time** คือเวลาที่ผ่านไปทั้งหมดตั้งแต่ flow item (หัวข้อ 2.2) เข้าสู่สายธารคุณค่าจนถึงตอนที่ส่งมอบ
วัดความรวดเร็วในการตอบสนองตลอดเส้นทางตั้งแต่ระบุความต้องการทางธุรกิจจนถึงตอนที่ลูกค้าได้รับคุณค่า
ส่วน **flow load** คือจำนวน flow item ทั้งหมดที่กำลังดำเนินอยู่หรือรออยู่ในสายธารคุณค่า ณ ขณะใดขณะหนึ่ง
เป็นชื่อที่ Flow Framework ใช้เรียกสิ่งที่หัวข้อ 2.5 เรียกว่างานระหว่างทำ (work in process)
สองตัวนี้รวมกันเป็นตัวชี้วัด Flow Framework สองตัวที่เชื่อมกับคณิตศาสตร์ของทฤษฎีคิวโดยตรงที่สุด
เพราะ flow load ไม่ได้แค่สัมพันธ์กับ flow time แต่กำหนดมันตามหลักคณิตศาสตร์

ความสัมพันธ์นั้นคือ **[กฎของลิตเติล (Little's law)](https://en.wikipedia.org/wiki/Little%27s_law)**
บทพิสูจน์จากทฤษฎีคิว (หัวข้อ 2.7 ครอบคลุมโดยละเอียด) ซึ่งกล่าวว่า
จำนวน item เฉลี่ยในระบบที่เสถียรเท่ากับอัตราการเข้าเฉลี่ยคูณด้วยเวลาเฉลี่ยที่แต่ละ item อยู่ในระบบ
เมื่อนำมาใช้ที่นี่ flow load เท่ากับอัตราการเข้าคูณ flow time
นี่คือข้อเท็จจริงที่มีประโยชน์ที่สุดข้อเดียวของหัวข้อนี้
เพราะมันเปลี่ยนข้อโต้แย้งที่เคยเป็นเชิงคุณภาพว่า "เราโหลดเกิน งานเลยช้า"
ให้เป็นข้อโต้แย้งเชิงปริมาณที่พิสูจน์ได้ ซึ่งผู้นำธุรกิจปัดตกได้ยาก
ถ้า flow load ยังเพิ่มขึ้นขณะที่อัตราการเข้าคงที่ flow time ก็รับประกันตามหลักคณิตศาสตร์ว่าจะเพิ่มด้วย ไม่ใช่แค่น่าจะเพิ่ม

สำหรับทีมขนาดใหญ่ นี่มักเป็นตัวเลขที่โน้มน้าวใจได้มากที่สุดตัวเดียวในกรอบทั้งหมด
ผู้นำธุรกิจที่ต้านการปฏิเสธงานใหม่เพราะทุกคำขอดูมีเหตุผลเมื่อมองแยกกัน
มักยอมรับว่าการโหลดสายธารคุณค่าเกินทำให้ทุก item ที่อยู่ในนั้นช้าลงได้พิสูจน์
เมื่อติดตาม flow load และแสดงความสัมพันธ์กับ flow time ให้เห็นตรง ๆ แทนที่จะเถียงเชิงนามธรรม
องค์กรขนาดใหญ่ที่ต้องรับมือกับโครงการเชิงกลยุทธ์พร้อมกันจำนวนมาก
และโครงการภาครัฐที่เดินสายงานขนานกันหลายสิบสาย
ต่างพึ่งบทพิสูจน์นี้ ไม่ใช่แค่สัญชาตญาณเบื้องหลัง
เพื่อให้เหตุผลในการปฏิเสธการเริ่มงานเพิ่มพร้อมกัน

## หลักการสำคัญ

- **Flow load กำหนด flow time ตามหลักคณิตศาสตร์ ผ่านกฎของลิตเติล**
  นี่ไม่ใช่ความสัมพันธ์เชิงสถิติ แต่เป็นบทพิสูจน์ที่ใช้ได้กับสายธารคุณค่าที่เสถียรทุกสาย
- **Flow time ครอบคลุมทั้งสายธารคุณค่า ไม่ใช่แค่ฝ่ายวิศวกรรม**
  เริ่มนับเมื่อระบุความต้องการทางธุรกิจ ไม่ใช่เมื่อฝ่ายวิศวกรรมรับงาน
  ซึ่ง cycle time ของหัวข้อ 2.6 จะแยกย่อยต่อไป
- **Flow load ที่เพิ่มขึ้นคือสัญญาณเตือนแรกสุดของ flow time ที่เพิ่มขึ้น**
  เพราะความสัมพันธ์พิสูจน์ได้ จึงเฝ้าดู flow load เป็นตัวชี้วัดนำได้
  ไม่ใช่แค่พบหลังจาก flow time แย่ลงไปแล้ว
- **จุดเข้าของสายธารคุณค่าต้องกำหนดและบันทึกไว้ให้แน่นอน**
  จุดที่นาฬิกา flow time เริ่มเดินเป็นการเลือกเชิงนิยามที่เปราะต่อความเสี่ยงด้านการเล่นแร่แปรธาตุตัวเลขเหมือนขอบเขตตัวชี้วัดอื่นทุกตัวในหนังสือเล่มนี้
- **ผู้นำธุรกิจลงมือกับ flow load ได้โดยตรง**
  ต่างจาก flow time ซึ่งเป็นการวัดแบบตามหลัง flow load เป็นคันโยก
  การปฏิเสธการเริ่มงานใหม่คือการกระทำที่ทำได้ตั้งแต่วันนี้

## ข้อเสนอแนะ

### กำหนดและบันทึกจุดเข้าของสายธารคุณค่าก่อนวัด flow time

ตัดสินใจอย่างชัดเจนว่า flow time เริ่มเมื่อระบุความต้องการทางธุรกิจครั้งแรก เมื่ออนุมัติอย่างเป็นทางการ
หรือเมื่อฝ่ายวิศวกรรมเริ่มลงมือ
และบันทึกการเลือกนั้นแบบเดียวกับที่หัวข้อ 1.4 แนะนำสำหรับกฎบัตรตัวชี้วัดทุกฉบับ
การตัดสินใจเพียงข้อนี้ข้อเดียวกำหนดว่า flow time วัดความรวดเร็วในการตอบสนองแบบต้นทางถึงปลายทางจริง
หรือแค่ส่วนที่แคบกว่าที่ฝ่ายวิศวกรรมควบคุมได้
และการเปลี่ยนนิยามภายหลังโดยไม่เปิดเผยคือความเสี่ยงด้านการเล่นแร่แปรธาตุตัวเลขหลักของหัวข้อนี้

### ติดตาม flow load อย่างต่อเนื่อง ไม่ใช่เป็นระยะ

เพราะ flow load เป็นตัวชี้วัดนำ ผ่านกฎของลิตเติล สำหรับ flow time ที่กำลังจะมา
ให้ติดตามเป็นตัวเลขสดที่อัปเดตต่อเนื่อง แทนที่จะเป็นภาพนิ่งตามรอบ
flow load ที่ไต่ขึ้นมาหลายสัปดาห์แล้วตอนที่มีคนไปดู
ได้ยืด flow time อย่างเงียบ ๆ มาเป็นเวลาเท่า ๆ กันโดยไม่มีใครเห็น ก่อนที่ตัวชี้วัดจะตามทัน

### ใช้กฎของลิตเติลอย่างชัดแจ้งเมื่อโต้แย้งเพื่อกำหนดขีดจำกัด WIP หรือเพิ่มกำลังคน

เมื่อเสนอให้เริ่มงานพร้อมกันน้อยลง หรือเพิ่มกำลังคน
ให้แสดงสมการจริง ไม่ใช่แค่ข้อเสนอ
คือ flow load เท่ากับอัตราการเข้าคูณ flow time
ดังนั้นถ้าอัตราการเข้าค่อนข้างคงที่ การลด flow load รับประกันตามหลักคณิตศาสตร์ว่าจะลด flow time
นี่เป็นข้อโต้แย้งที่แข็งกว่ามากต่อผู้มีส่วนได้ส่วนเสียที่ไม่เชื่อ
เมื่อเทียบกับการอ้างลอย ๆ ว่า "เรายุ่งเกินไป" เพราะพิสูจน์ได้ ไม่ใช่แค่ยืนยัน

### แยก flow time ออกจากสาเหตุเบื้องหลังของ flow load ก่อนเสนอวิธีแก้

เมื่อ flow load สูง ให้สืบว่า flow item ประเภทใด (หัวข้อ 2.2) เป็นตัวขับจริง
เริ่มฟีเจอร์พร้อมกันมากเกินไป backlog ข้อบกพร่องที่ไม่มีใครแตะ
หรืองานความเสี่ยงที่ติดรอการอนุมัติร่วม
แต่ละสาเหตุบ่งชี้วิธีแก้ต่างกัน
และการมอง "flow load สูง" เป็นปัญหาเดียวที่ไม่แยกแยะมักให้การตอบสนองแบบทั่วไปที่ไม่ได้ผล

### ตรวจข้าม flow time กับ cycle time เพื่อแยกว่าความล่าช้าเกิดตรงไหนจริง

เนื่องจาก flow time ครอบคลุมทั้งสายธารคุณค่า ส่วน cycle time (หัวข้อ 2.6) ครอบคลุมเฉพาะส่วนวิศวกรรม
ให้เปรียบเทียบสองตัวนี้โดยตรง
ช่องว่างใหญ่ระหว่าง flow time กับ cycle time หมายความว่าความล่าช้าส่วนใหญ่เกิดก่อนที่ฝ่ายวิศวกรรมจะเห็นงานเสียอีก
ในคิวอนุมัติ backlog การจัดลำดับความสำคัญ หรือจุดส่งต่อระหว่างทีม
ซึ่งชี้ไปทางวิธีแก้ที่ต่างจากช่องว่างที่กระจุกอยู่ภายในฝ่ายวิศวกรรมเองมาก

## ข้อแลกเปลี่ยน: ข้อดีและข้อเสีย

| แนวทาง | ข้อดี | ข้อเสีย |
| --- | --- | --- |
| วัด flow time จากตอนที่ฝ่ายวิศวกรรมรับงานเท่านั้น | เรียบง่าย ตรงกับเครื่องมือวัด cycle time ที่มีอยู่ | พลาดความล่าช้าก่อนฝ่ายวิศวกรรม ประเมินความรวดเร็วจริงต่ำเกินไป |
| วัด flow time จากตอนระบุความต้องการทางธุรกิจจริง | จับความรวดเร็วแบบต้นทางถึงปลายทางจริง | ต้องติดตั้งเครื่องมือวัดในขั้นตอนที่อยู่นอกการควบคุมโดยตรงของฝ่ายวิศวกรรม |
| ภาพนิ่ง flow load เป็นระยะ | คำนวณนาน ๆ ครั้งถูก | เสียคุณค่าของตัวชี้วัดนำ โหลดที่เพิ่มขึ้นไม่มีใครสังเกตนานเกินไป |
| ติดตาม flow load ต่อเนื่อง | ตัวชี้วัดนำแบบสดที่ลงมือได้ | ต้องผนวกเครื่องมืออย่างต่อเนื่อง ไม่ใช่แค่รายงานนาน ๆ ครั้ง |

ความตึงเครียดหลักคือ **ขอบเขตเทียบกับระยะที่เครื่องมือวัดเอื้อมถึง**
การวัด flow time จากตอนที่ฝ่ายวิศวกรรมรับงานอย่างเดียวติดตั้งเครื่องมือง่ายกว่ามาก
เพราะใช้ข้อมูล cycle time ที่หัวข้อ 2.6 เก็บอยู่แล้ว
แต่มันประเมินความรวดเร็วจริงต่ำเกินไปอย่างเงียบ ๆ ด้วยการมองข้ามทุกอย่างที่เกิดก่อนฝ่ายวิศวกรรมเห็นงาน
วิธีคลายความตึงเครียดคือเริ่มจากการวัดที่แคบกว่าและจำกัดอยู่ที่ฝ่ายวิศวกรรม ถ้านั่นคือทั้งหมดที่ติดตั้งได้วันนี้
แต่ให้มองการขยายจุดเริ่มของ flow time ย้อนขึ้นไปต้นน้ำ ไปสู่การระบุความต้องการทางธุรกิจและการจัดลำดับความสำคัญ
เป็นลำดับความสำคัญระยะใกล้ ไม่ใช่ข้อจำกัดถาวร

## คำถามเพื่อหารือกับทีมของคุณ

1. **นาฬิกา flow time ของเราเริ่มนับจากตรงไหนในวันนี้ และทุกคนในองค์กรเห็นพ้องหรือไม่ว่าเป็นจุดเริ่มที่ถูก?**
   ความไม่ตรงกันระหว่างจุดที่ผู้มีส่วนได้ส่วนเสียคิดว่านาฬิกาเริ่มกับจุดที่มันเริ่มจริง
   เป็นต้นเหตุเงียบ ๆ ที่พบบ่อยของความไม่ไว้วางใจตัวชี้วัด
   ยืนยันว่านิยามที่บันทึกไว้ตรงกับความเข้าใจร่วมกัน

2. **เราเคยตรวจหรือไม่ว่า flow load, อัตราการเข้า และ flow time ที่วัดได้เป็นไปตามกฎของลิตเติลจริง?**
   ถ้าไม่สมดุลกันโดยประมาณ แสดงว่ามีตัวเลขหนึ่งในสามที่วัดไม่สม่ำเสมอ
   ไล่ดูตัวเลขจริงด้วยกัน แทนที่จะสมมติว่าการตรวจจะผ่าน

3. **เราติดตาม flow load อย่างต่อเนื่องหรือไม่ หรือการเพิ่มขึ้นอย่างสม่ำเสมออาจไม่มีใครสังเกตหลายสัปดาห์ก่อนจะมีใครไปดู?**
   ตัวชี้วัดนำปกป้องคุณได้ก็ต่อเมื่อมีคนเฝ้าดูมันเกือบเรียลไทม์จริง ๆ
   ไม่ใช่แค่ทบทวนในรายงานรายไตรมาส

4. **เมื่อ flow load เพิ่มขึ้น เราบอกได้หรือไม่ว่า flow item ประเภทใดเป็นตัวขับ หรือมันอ่านออกมาเป็นตัวเลขเดียวที่ไม่แยกแยะ?**
   การวินิจฉัยแบบทั่วไปว่า "เราโหลดเกิน" ให้การตอบสนองแบบทั่วไปที่มักไม่ได้ผล
   ตรวจว่าเครื่องมือวัดปัจจุบันของคุณระบุสาเหตุเฉพาะของโหลดที่เพิ่มขึ้นได้จริงหรือไม่

5. **ช่องว่างระหว่าง flow time กับ cycle time ของเราใหญ่แค่ไหน
   และช่องว่างนั้นบอกว่าความล่าช้าส่วนใหญ่เกิดก่อนหรือหลังฝ่ายวิศวกรรมเห็นงาน?**
   การเปรียบเทียบนี้มักเผยว่าโอกาสปรับปรุงที่ใหญ่ที่สุดอยู่นอกการควบคุมของฝ่ายวิศวกรรมเองทั้งหมด

6. **เคยมีใครแอบทำให้จุดเริ่มของ flow time แคบลงเพื่อให้ตัวเลขดูดีขึ้น
   โดยไม่บันทึกหรือเปิดเผยการเปลี่ยนนั้นหรือไม่?**
   นี่คือความเสี่ยงด้านการเล่นแร่แปรธาตุตัวเลขหลักของหัวข้อนี้ที่พูดตรง ๆ
   ถามตัวเองอย่างซื่อสัตย์ว่านิยามของคุณเคยเบี่ยงไปในทางนี้หรือไม่

## มุมมองตามภาคส่วน

**สตาร์ทอัป** Flow load มักต่ำเพราะคนไม่พอจะเริ่มงานพร้อมกันได้มาก
แต่ความสัมพันธ์ทางคณิตศาสตร์เดียวกันใช้ได้ทันทีที่ผู้ก่อตั้งหรือวิศวกรนำกลายเป็นคอขวดส่วนตัวของหลายโครงการพร้อมกัน
ติดตาม flow load แบบไม่เป็นทางการแม้ไม่มีเครื่องมือเฉพาะ เพราะกฎของลิตเติลใช้ได้ไม่ว่าขนาดใด

**ธุรกิจขนาดเล็ก** รายการร่วมง่าย ๆ ของทุกสิ่งที่กำลังดำเนินอยู่มักพอสำหรับคำนวณ flow load
โดยไม่ต้องมีซอฟต์แวร์บริหารสายธารคุณค่าโดยเฉพาะ
นิสัยที่มีประโยชน์คือเช็กบ่อยพอที่จะจับตัวเลขที่เพิ่มขึ้นได้เร็ว
ไม่ใช่มาพบเมื่อ flow time แย่ลงให้เห็นชัดแล้ว

**องค์กรขนาดใหญ่** ที่นี่คือที่ที่กฎของลิตเติลสร้างคุณค่าในฐานะข้อโต้แย้ง ไม่ใช่แค่ตัวชี้วัด
องค์กรใหญ่ที่ต้องรับมือโครงการเชิงกลยุทธ์พร้อมกันหลายสิบโครงการ
ใช้ความสัมพันธ์ที่พิสูจน์ได้ระหว่าง flow load กับ flow time เพื่อเสนอข้อโต้แย้งอิงหลักฐานให้จัดลำดับงาน
สิ่งที่ข้อโต้แย้ง "เรายุ่งเกินไป" เชิงคุณภาพล้วน ๆ แทบทำไม่สำเร็จเมื่อเจอแรงกดดันที่แน่วแน่จากผู้มีส่วนได้ส่วนเสีย

**ภาครัฐ** โครงการหลายปีสะสม flow load ที่ใหญ่และซ่อนอยู่ข้ามสายงานจำนวนมากเป็นปกติ
แต่ละสายมีเหตุผลรองรับเมื่อมองแยก โดยไม่มีใครเห็นยอดรวมทั้งองค์กร
การนำเสนอกฎของลิตเติลตรง ๆ
แสดงว่าการเพิ่มขึ้นของ flow time ของโครงการอธิบายได้ด้วยคณิตศาสตร์จาก flow load ที่เพิ่มขึ้นของโครงการเอง
มักเป็นหลักฐานที่ชัดและโน้มน้าวใจที่สุดสำหรับการจัดลำดับสายงาน แทนที่จะเดินทุกสายพร้อมกันไปเรื่อย ๆ

## ตัวอย่าง

**องค์กรขนาดใหญ่** องค์กรแพลตฟอร์มของบริษัทเทคโนโลยีสื่อกำลังเดินโครงการเชิงกลยุทธ์พร้อมกันยี่สิบสองโครงการ
ในขณะที่กำลังคนเหมาะกับราวสิบสอง
ความไม่ตรงกันที่ไม่มีใครเคยวัดเป็นตัวเลข จนรองประธานฝ่ายวิศวกรรมคนใหม่ขอดู flow load โดยตรง
flow time ของโครงการค่ามัธยฐานเพิ่มขึ้น 40% ในปีที่ผ่านมา
แนวโน้มที่ผู้บริหารเคยอธิบายว่า "งานยากขึ้น"
การนำเสนอกฎของลิตเติลควบคู่กับตัวเลข flow load และอัตราการเข้าจริงแสดงว่า
การเพิ่มขึ้นนั้นอธิบายได้ครบด้วย flow load ที่เพิ่มขึ้นอย่างเดียว
โดยไม่ต้องอาศัยความยากของงานที่เปลี่ยนไปมาอธิบายเลย
องค์กรจัดลำดับโครงการลงมาให้เหลือ flow load ที่ยั่งยืน
และ flow time ค่ามัธยฐานลดลงเกือบหนึ่งในสามภายในสองไตรมาส

**ภาครัฐ** โครงการปรับปรุงของหน่วยงานบริหารเงินอุดหนุนระดับรัฐบาลกลางสะสม flow load
ข้ามสายงานขนานหลายสิบสายโดยไม่มียอดรวมที่ติดตามอยู่เลย
ผู้สนับสนุนแต่ละสายเชื่อว่าโครงการของตนมีทรัพยากรเหมาะสมเมื่อมองแยก
การวิเคราะห์ของสำนักงานโครงการด้วยกฎของลิตเติลแสดงว่า
flow time รวมของโครงการ คือเวลาจากการอนุมัติสายงานถึงการส่งมอบ
ทำนายได้เกือบเป๊ะจาก flow load รวมเพียงอย่างเดียว
ข้อค้นพบที่โน้มน้าวผู้สนับสนุนที่ต้านข้อโต้แย้งเรื่องการลดลำดับความสำคัญมานานกว่าหนึ่งปี
โครงการจึงกำหนดเพดาน flow load อย่างชัดเจน
และสายงานใหม่ต้องเข้าคิวแทนที่จะเริ่มทันทีโดยไม่คำนึงถึงโหลดปัจจุบัน

## เหตุผลทางธุรกิจ: แรงจูงใจ ROI และ TCO

ผลตอบแทนของการติดตาม flow load และ flow time ด้วยกันคือเหตุผลที่พิสูจน์ได้ ไม่ใช่แค่โน้มน้าวใจ
สำหรับการจัดลำดับงานแทนที่จะเดินทุกอย่างขนานกัน
ตัวอย่างบริษัทเทคโนโลยีสื่อข้างต้นที่อธิบายการถดถอยของ flow time ทั้งหมดด้วย flow load อย่างเดียว
คือรูปแบบที่การรวมกันนี้ให้ผลได้อย่างเชื่อถือได้
คือข้อโต้แย้งเชิงปริมาณเฉพาะเจาะจงสำเร็จในที่ที่การอ้างเชิงคุณภาพว่า "ยุ่งเกินไป" เคยล้มเหลว
เมื่อเจอแรงกดดันจริงในองค์กรที่อยากเริ่มงานเพิ่ม

ต้นทุนรวมในการเป็นเจ้าของต่ำเมื่อเทียบกับพลังโน้มน้าวของมัน
flow load ต้องการเพียงการนับสดของ item ที่กำลังดำเนินอยู่และรออยู่
และ flow time ต้องติดตั้งเครื่องมือวัดที่จุดเข้าของสายธารคุณค่า
งานที่คุ้มค่าตัวเองตั้งแต่ครั้งแรกที่มันป้องกันไม่ให้องค์กรรับปากโครงการพร้อมกันมากกว่าที่กำลังคนจริงรองรับได้

## แอนตี้แพตเทิร์นและข้อผิดพลาด

- **แอบทำให้จุดเริ่มของ flow time แคบลงเพื่อให้ตัวเลขดูดี:**
  gaming vector ที่เป็นหัวใจของหัวข้อนี้
  การย้ายจุดเริ่มของนาฬิกาจากการระบุความต้องการทางธุรกิจจริงไปยังจุดที่หลังกว่า
  เช่นตอนฝ่ายวิศวกรรมรับงานหรือตอนอนุมัติอย่างเป็นทางการ
  ทำให้ flow time หดลงโดยไม่ได้เปลี่ยนความรวดเร็วในการตอบสนองจริงเลย
  และอาจเกิดช้า ๆ จนไม่มีการเปลี่ยนครั้งใดดูเหมือนการบิดเบือนโดยเจตนา
  guardrail คือบันทึกจุดเข้าอย่างชัดเจนในกฎบัตรตัวชี้วัด (หัวข้อ 1.4)
  และตรวจสอบเป็นระยะเทียบกับนิยามที่บันทึกไว้
  เป็นวินัยเดียวกับที่หนังสือเล่มนี้ขอกับขอบเขตของตัวชี้วัดทุกตัว
- **วัด flow load เป็นระยะเท่านั้น:**
  เสียคุณค่าในฐานะตัวชี้วัดนำ เพราะการเพิ่มขึ้นอย่างสม่ำเสมออาจไม่มีใครสังเกตหลายสัปดาห์
- **มอง flow load เป็นตัวเลขเดียวที่ไม่แยกแยะ:**
  พลาดว่า flow item ประเภทใดเป็นตัวขับโหลดเกินจริง ให้การตอบสนองแบบทั่วไปแทนที่จะตรงจุด
- **ละเลยช่องว่างระหว่าง flow time กับ cycle time:**
  พลาดว่าความล่าช้ากระจุกอยู่ก่อนหรือหลังฝ่ายวิศวกรรม ซึ่งบ่งชี้วิธีแก้ต่างกันมาก
- **โต้แย้งให้ลดงานพร้อมกันโดยไม่แสดงกฎของลิตเติลอย่างชัดแจ้ง:**
  ข้ออ้างเชิงคุณภาพปัดตกง่ายกว่าความสัมพันธ์เชิงปริมาณที่พิสูจน์ได้มากสำหรับผู้มีส่วนได้ส่วนเสีย
- **สมมติว่ากฎของลิตเติลใช้เฉพาะในระดับใหญ่:**
  มันใช้ได้กับระบบที่เสถียรทุกขนาด รวมถึงบุคคลคนเดียวที่โหลดเกิน

## แบบจำลองวุฒิภาวะ

- **ระดับ 1 เริ่มต้น (Initiate):** ไม่ติดตามทั้ง flow time และ flow load
  พูดถึงความล่าช้าแบบเล่าสู่กันฟังโดยไม่มีข้อมูลรองรับ
- **ระดับ 2 พัฒนา (Develop):** ติดตาม flow time จากตอนที่ฝ่ายวิศวกรรมรับงานเท่านั้น
  และตรวจ flow load เป็นระยะแทนที่จะต่อเนื่อง
- **ระดับ 3 มาตรฐาน (Standardize):** วัด flow time จากจุดเข้าของสายธารคุณค่าที่บันทึกไว้และใช้ทั้งองค์กร
  และติดตาม flow load อย่างต่อเนื่องเป็นตัวชี้วัดนำ
- **ระดับ 4 บริหารจัดการ (Manage):** ใช้กฎของลิตเติลอย่างชัดแจ้งเพื่อให้เหตุผลการตัดสินใจเรื่องกำลังคนและการจัดลำดับ
  และระบุ flow load ที่เพิ่มขึ้นว่าเกิดจาก flow item ประเภทใดก่อนเสนอวิธีแก้
- **ระดับ 5 ประสาน (Orchestrate):** องค์กรกำหนดเพดาน flow load อย่างชัดเจนข้ามสายธารคุณค่า
  และชี้ได้ถึงการตัดสินใจจัดลำดับเฉพาะ ซึ่งมีกฎของลิตเติลหนุน และทำให้ flow time ดีขึ้นอย่างวัดผลได้

## ประเด็นเพื่อการอภิปราย

1. นาฬิกา flow time ของเราเริ่มนับจากตรงไหนจริง และนิยามนั้นเคยเบี่ยงโดยไม่มีการบันทึกหรือไม่?
2. flow load, อัตราการเข้า และ flow time ที่เราวัดได้เป็นไปตามกฎของลิตเติลโดยประมาณหรือไม่?
3. เราติดตาม flow load ต่อเนื่องพอที่จะจับการเพิ่มขึ้นอย่างสม่ำเสมอได้ภายในไม่กี่วัน ไม่ใช่หลายเดือนหรือไม่?
4. ช่องว่างระหว่าง flow time กับ cycle time ของเราเป็นเท่าไร และช่องว่างนั้นบอกอะไรเราว่าความล่าช้าเกิดตรงไหนจริง?

## ข้อสรุปสำคัญ

- **Flow load กำหนด flow time ตามหลักคณิตศาสตร์** ผ่านกฎของลิตเติล
  flow load เท่ากับอัตราการเข้าคูณ flow time สำหรับสายธารคุณค่าที่เสถียรทุกสาย
- **Flow time ครอบคลุมทั้งสายธารคุณค่า** ตั้งแต่การระบุความต้องการทางธุรกิจจนถึงการส่งมอบ
  กว้างกว่าขอบเขตเฉพาะฝ่ายวิศวกรรมของ cycle time (หัวข้อ 2.6)
- gaming vector หลักของหัวข้อนี้คือ **การแอบทำให้จุดเริ่มของ flow time แคบลง**
  guardrail คือนิยามจุดเข้าที่บันทึกไว้และตรวจสอบสม่ำเสมอ
- **ติดตาม flow load อย่างต่อเนื่อง** ไม่ใช่เป็นระยะ เพื่อให้ทำหน้าที่เป็นตัวชี้วัดนำจริง
  แทนที่จะเป็นการค้นพบแบบตามหลัง
- ใช้กฎของลิตเติล **อย่างชัดแจ้ง** ไม่ใช่แค่เป็นสัญชาตญาณ
  เมื่อโต้แย้งเพื่อกำหนดขีดจำกัด WIP เพิ่มกำลังคน หรือจัดลำดับงานที่เดินพร้อมกัน
