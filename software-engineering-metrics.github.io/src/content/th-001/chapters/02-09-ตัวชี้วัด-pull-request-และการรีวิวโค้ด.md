# 2.9 ตัวชี้วัด pull request และการรีวิวโค้ด

## ภาพรวมและแรงจูงใจ

[การรีวิวโค้ด (Code review)](https://en.wikipedia.org/wiki/Code_review) มักเป็นส่วนที่เพิ่มเวลารอมากที่สุดในการแยก cycle time จากหัวข้อ 2.6 และยังเป็นขั้นตอนที่ทีมปรับปรุงได้เองโดยตรงที่สุด ต่างจากคอขวดของแพลตฟอร์มร่วมหรือการพึ่งพาภายนอก หัวข้อนี้ครอบคลุมตัวชี้วัดเฉพาะที่อยู่ภายในขั้นตอนรีวิว ได้แก่ เวลาถึงรีวิวครั้งแรก ขนาดของ pull request จำนวนรอบของการรีวิว และการกระจายภาระของผู้รีวิว และวิธีใช้ตัวชี้วัดเหล่านี้ปรับปรุงความเร็วของการรีวิวโดยไม่สละประโยชน์ด้านคุณภาพที่การรีวิวควรให้

ความเสี่ยงที่หัวข้อนี้ระวังที่สุดเป็นสิ่งที่หนังสือเล่มนี้ยังไม่ได้พูดถึงโดยตรง คือการเร่งความเร็วรีวิวอาจกัดกร่อนคุณภาพรีวิวอย่างเงียบ ๆ ถ้าทำโดยไม่ระวัง ทีมที่ลดเวลาถึงรีวิวครั้งแรกลงครึ่งหนึ่งด้วยการอนุมัติทุกอย่างแบบประทับตราได้ปรับปรุงตัวชี้วัดหนึ่งตัว แต่ทำลายคุณค่าจริงของแนวปฏิบัตินั้นไป ทุกข้อเสนอแนะในหัวข้อนี้เขียนขึ้นโดยคำนึงถึงข้อแลกเปลี่ยนนี้ เพราะตัวชี้วัดของ pull request เป็นกลุ่มที่เล่นแร่แปรธาตุได้ง่ายที่สุดกลุ่มหนึ่งในหนังสือเล่มนี้ ให้ดูดีบนแดชบอร์ดขณะที่ทำให้โค้ดเบสแย่ลงอย่างวัดได้

สำหรับทีมขนาดใหญ่ ตัวชี้วัดการรีวิวเผยปัญหาการถ่วงดุลภาระที่มองไม่เห็นในทางอื่น เช่น วิศวกรอาวุโสจำนวนน้อยรับภาระรีวิวไปมากเกินส่วน ทีมหรือส่วนของโค้ดเบสที่การรีวิวติดขัดซ้ำ ๆ หรือรูปแบบของ pull request ที่ใหญ่เกินจนการรีวิวอย่างรอบคอบเป็นไปไม่ได้ในทางปฏิบัติ ไม่ว่าผู้รีวิวจะขยันแค่ไหน รูปแบบเหล่านี้ทบกันมากในระดับใหญ่กว่าในทีมเล็ก ซึ่งทุกคนเห็นความไม่สมดุลได้โดยตรงโดยไม่ต้องมีตัวชี้วัดมาเผย

## หลักการสำคัญ

- **เวลาถึงรีวิวครั้งแรกมักเป็นคันโยกที่ใหญ่ที่สุด ไม่ใช่ความละเอียดของการรีวิวเอง** ความล่าช้าส่วนใหญ่มาจาก pull request ที่รอให้คนมาดู ไม่ใช่จากบทสนทนารีวิวที่ใช้เวลานานเมื่อเริ่มแล้ว
- **pull request ที่เล็กกว่าถูกรีวิวเร็วกว่าและละเอียดกว่า ไม่ใช่แค่เร็วกว่า** ขนาดเป็นจุดงัดที่ได้ทั้งความเร็วและคุณภาพพร้อมกัน
- **ความเร็วและคุณภาพของการรีวิวไม่ได้ขัดกันโดยอัตโนมัติ แต่แลกกันอย่างไม่ระวังได้** ป้องกันการแลกนั้นอย่างชัดเจน
- **ภาระผู้รีวิวที่ไม่สมดุลเป็นเรื่องปกติและมักมองไม่เห็นถ้าไม่มีตัวชี้วัด** คนจำนวนน้อยมักรับส่วนที่มากเกินสัดส่วน
- **ตัวชี้วัดเหล่านี้เสี่ยงต่อการถูกเล่นแบบประทับตรา** การอนุมัติเร็วโดยไม่มีการตรวจจริงทำลายจุดประสงค์ทั้งหมดของการรีวิว

## ข้อเสนอแนะ

### ติดตามเวลาถึงรีวิวครั้งแรกเป็นตัวชี้วัดความเร็วหลัก

วัดช่วงเวลาตั้งแต่เปิด pull request จนถึงความคิดเห็นเชิงเนื้อหาครั้งแรกหรือการอนุมัติของผู้รีวิว โดยเก็บอัตโนมัติจากแพลตฟอร์ม version control ของคุณ นี่มักเป็นส่วนที่เพิ่มเวลารอมากที่สุดในขั้นตอนรีวิว (หัวข้อ 2.5 หัวข้อ 2.6) และการปรับปรุงมัน ด้วยแนวปฏิบัติการมอบหมายผู้รีวิวที่ชัดเจนขึ้น วิธีแจ้งเตือน หรือการกันเวลาเฉพาะสำหรับรีวิว มักให้การปรับปรุง cycle time โดยรวมครั้งเดียวที่ใหญ่ที่สุดที่ทีมทำได้

### ติดตามขนาดของ pull request และส่งเสริมการเปลี่ยนแปลงที่เล็กลงอย่างจริงจัง

วัดจำนวนบรรทัดที่เปลี่ยนหรือจำนวนไฟล์ที่แตะต่อ pull request และมองขนาดมัธยฐานที่ใหญ่อย่างต่อเนื่องเป็นสัญญาณที่ควรจัดการโดยตรง pull request ที่เล็กกว่าถูกรีวิวเร็วกว่า ละเอียดกว่า (ผู้รีวิวเก็บการเปลี่ยนแปลงทั้งหมดไว้ในหัวได้จริง) และย้อนกลับได้ง่ายกว่าถ้ามีอะไรผิดพลาด ซึ่งเชื่อมกลับไปถึงหลักการขนาดล็อต (batch size) เบื้องหลังความถี่การดีพลอยในหัวข้อ 2.10 ส่งเสริมให้แยกการเปลี่ยนแปลงใหญ่เป็นลำดับของ pull request เล็ก ๆ ที่รีวิวได้เป็นอิสระต่อกัน ทุกที่ที่งานเอื้อ

### เฝ้าดูการกระจายภาระของผู้รีวิวอย่างชัดเจน

ติดตามจำนวนรีวิวที่แต่ละคนทำเสร็จในช่วงเวลาแบบเลื่อน และเฝ้าดูโดยเฉพาะว่ามีคนจำนวนน้อยรับส่วนที่มากเกินสัดส่วนหรือไม่ รูปแบบนี้พบบ่อย มักตกอยู่กับวิศวกรที่อาวุโสที่สุดหรือที่ได้รับความไว้ใจมากที่สุด และสร้างทั้งคอขวด (ความพร้อมของพวกเขาเป็นเพดานของ throughput การรีวิวของทั้งทีม) และความเสี่ยงต่อภาวะหมดไฟ (หัวข้อ 3.2 ครอบคลุมตัวชี้วัดความเป็นอยู่ที่ดีอย่างลึกกว่า) หมุนเวียนความรับผิดชอบด้านรีวิวอย่างตั้งใจ แทนที่จะปล่อยให้กระจุกตัวโดยปริยายรอบคนที่ตอบเร็วที่สุด

### ป้องกันความเสี่ยงของการรีวิวแบบประทับตราอย่างชัดเจน

จับคู่เวลาถึงรีวิวครั้งแรกกับสัญญาณคุณภาพ คือ อัตราข้อบกพร่องหรือเหตุขัดข้องที่สืบกลับไปถึงการเปลี่ยนแปลงที่ถูกอนุมัติโดยไม่มีความคิดเห็นรีวิวเลย หรืออัตราการแก้ไขหลัง merge ที่ต้องทำกับโค้ดที่เพิ่งผ่านรีวิว ทีมที่ปรับปรุงความเร็วรีวิวด้วยการอนุมัติโดยไม่ตรวจจริงควรเห็น guardrail นี้เสื่อมลง ซึ่งเป็นหลักการจับคู่จากหัวข้อ 1.2 ที่ใช้กับตระกูลตัวชี้วัดนี้โดยเฉพาะ อย่าไล่ตามความเร็วรีวิวโดยไม่มีตัวชี้วัดถ่วงนี้อยู่ในสายตา

### ใช้จำนวนรอบรีวิวเพื่อมองหาแรงเสียดทาน ไม่ใช่เพื่อตัดสินตัวบุคคล

จำนวนรอบรีวิวที่ pull request ผ่านก่อน merge บ่งชี้แรงเสียดทานจริงได้ เช่น ความต้องการที่ไม่ชัด ความเห็นต่างเรื่องแนวทาง ความคาดหวังด้านสไตล์ที่ไม่สม่ำเสมอ ซึ่งควรสืบสวนในระดับกระบวนการ หลีกเลี่ยงการใช้ตัวเลขนี้ตัดสินผู้เขียนหรือผู้รีวิวรายบุคคลโดยตรง จำนวนรอบที่สูงมักเป็นสัญญาณของระบบหรือการสื่อสารมากกว่าเรื่องส่วนตัว และการมองมันเป็นสมุดคะแนนรายบุคคลเสี่ยงต่อการเลื่อนไหลไปสู่การประเมินตัวคนแบบที่หัวข้อ 1.1 เตือนไว้

## ข้อแลกเปลี่ยน: ข้อดีและข้อเสีย

| แนวทาง | ข้อดี | ข้อเสีย |
| --- | --- | --- |
| ปรับให้ดีที่สุดเฉพาะเวลาถึงรีวิวครั้งแรก | สัญญาณเร็ว ชัด วัดง่าย | อาจจูงใจให้รีวิวผิวเผินแบบประทับตราถ้าไม่มีการป้องกัน |
| ปรับให้ดีที่สุดเฉพาะการลดขนาด pull request | ปรับปรุงทั้งความเร็วและความละเอียดพร้อมกัน | งานทุกอย่างไม่ได้แยกเป็นส่วนเพิ่มเล็ก ๆ ได้สะอาด |
| หมุนเวียนภาระรีวิวให้เท่ากัน | ลดคอขวดและความเสี่ยงต่อภาวะหมดไฟ | อาจทำให้รีวิวช้าลงสำหรับโค้ดเฉพาะทางที่รีวิวยากและต้องการความเชี่ยวชาญเฉพาะ |
| รวมศูนย์การรีวิวไว้ที่วิศวกรอาวุโส | ใช้ความเชี่ยวชาญเชิงโดเมนอย่างลึกและสม่ำเสมอ | สร้างคอขวดและความเสี่ยงต่อภาวะหมดไฟเมื่อเวลาผ่านไป |

ความตึงเครียดหลักคือ **ความเร็วกับความลึกของการตรวจ** ทุกเทคนิคในหัวข้อนี้ที่เร่งการรีวิว ทั้งการตอบครั้งแรกให้เร็วขึ้น pull request ที่เล็กลง ภาระผู้รีวิวที่กระจายมากขึ้น มีความเสี่ยงที่จะแลกการตรวจจริงไปบ้าง ถ้าทำโดยไม่มี guardrail ด้านคุณภาพที่หัวข้อนี้แนะนำ คลี่คลายด้วยการจับคู่ตัวชี้วัดความเร็วทุกตัวกับสัญญาณคุณภาพที่ติดตามในช่วงเวลาเดียวกัน เพื่อให้ทีมแยกการปรับปรุงกระบวนการจริงออกจากมาตรฐานรีวิวที่กำลังเสื่อมลงอย่างเงียบ ๆ

## คำถามเพื่อหารือกับทีมของคุณ

1. **เวลาถึงรีวิวครั้งแรกจริงของเราเป็นเท่าไร และขั้นตอนรีวิวกินสัดส่วนเท่าไรของ cycle time รวม?** ดึงตัวเลขจริงแทนการอาศัยความรู้สึก เวลารอรีวิวมักมากกว่าที่ทีมคิด เพราะเวลาที่ใช้รอนั้นประเมินต่ำได้ง่ายกว่าเวลาที่ลงมือทำจริง

2. **ขนาด pull request มัธยฐานของเราเป็นเท่าไร และความล่าช้าในการรีวิวจะหดลงเท่าไรถ้าขนาดลดลง?** pull request ใหญ่ทั้งรีวิวช้ากว่าและมีแนวโน้มได้รับรีวิวผิวเผินมากกว่า เพียงเพราะผู้รีวิวเก็บทั้งหมดไว้ในหัวพร้อมกันไม่ได้ ดูการกระจายของขนาดจริง ไม่ใช่แค่มัธยฐาน

3. **ภาระรีวิวกระจุกอยู่กับคนจำนวนน้อยหรือไม่ และ throughput การรีวิวของเราจะเป็นอย่างไรถ้าหนึ่งในพวกเขาไม่อยู่สองสัปดาห์?** คำถามนี้เผยทั้งความเสี่ยงคอขวดและความเสี่ยงภาวะหมดไฟพร้อมกัน ดึงข้อมูลภาระผู้รีวิวจริงแทนการอาศัยความรู้สึก

4. **เราเคยปรับปรุงตัวชี้วัดความเร็วรีวิวในแบบที่เมื่อมองย้อนกลับไปแล้วทำให้การตรวจจริงลดลงหรือไม่?** ตอบตามจริง นี่คือความเสี่ยงแบบประทับตราที่หัวข้อนี้เรียกชื่อ และไถลเข้าไปได้ง่ายโดยไม่มีการตัดสินใจตั้งใจเลย

5. **จำนวนรอบรีวิวที่สูงมักบ่งบอกอะไรในทีมของเรา: ความเห็นต่างจริง ความต้องการที่ไม่ชัด หรือความคาดหวังด้านสไตล์ที่ไม่สม่ำเสมอ?** ดูตัวอย่าง pull request ที่มีจำนวนรอบสูงผิดปกติ และวินิจฉัยรูปแบบจริง แทนที่จะสมมุติว่ามันสะท้อนถึงความบกพร่องของผู้เขียนหรือผู้รีวิว

6. **เรามี guardrail ด้านคุณภาพจับคู่กับตัวชี้วัดความเร็วรีวิวหรือไม่ หรือเราติดตามความเร็วโดดเดี่ยว?** ถ้าคำตอบตรง ๆ คือไม่มี guardrail เช่นนั้น นั่นคือช่องว่างที่ควรปิดก่อนจะผลักความเร็วรีวิวต่อไป ตามหลักการจับคู่ของหัวข้อ 1.2

## มุมมองตามภาคส่วน

**สตาร์ทอัป** การรีวิวมักเร็วโดยค่าเริ่มต้นเมื่อทีมเล็ก บางครั้งเร็วเกินไปเกือบจะ คือรีวิวโดยผู้อนุมัติคนเดียวด้วยการตรวจน้อยที่สุดเพราะทุกคนไว้ใจกัน ความเสี่ยงที่ควรจับตาเมื่อทีมโตขึ้นคือคุณภาพรีวิวที่ไม่โตตามขนาดทีม เพราะความไว้ใจแบบไม่เป็นทางการที่ได้ผลกับวิศวกรห้าคนไม่ได้ใช้ได้โดยอัตโนมัติกับห้าสิบคน

**ธุรกิจขนาดเล็ก** แพลตฟอร์ม version control ส่วนใหญ่รายงานเวลาถึง merge และจำนวนรีวิวให้พร้อมใช้ ใช้ตัวเลขเหล่านี้แทนการสร้างเครื่องมือวัดเอง วินัยหลักที่ควรปลูกคือสังเกตว่าภาระรีวิวกระจุกตัวไปที่หนึ่งหรือสองคนอย่างเงียบ ๆ ตามที่ทีมโตขึ้นหรือไม่

**องค์กรขนาดใหญ่** ภาระผู้รีวิวที่ไม่สมดุลและคอขวดด้านความรู้เฉพาะทางพบได้บ่อยเป็นพิเศษที่นี่ ที่ความเชี่ยวชาญเชิงโดเมนลึกในระบบสำคัญอาจรวมความรับผิดชอบรีวิวไว้ที่กลุ่มเล็ก ๆ ไม่ว่าทีมจะใหญ่แค่ไหน ลงทุนในการแบ่งปันความรู้และการหมุนเวียนรีวิวอย่างตั้งใจเพื่อกระจายความเชี่ยวชาญ ลดทั้งคอขวดและความเสี่ยงแบบ bus factor ที่ความเชี่ยวชาญอยู่กับคนน้อยเกินไป

**ภาครัฐ** กระบวนการรีวิวที่นี่มักมีน้ำหนักด้านการปฏิบัติตามกฎระเบียบควบคู่กับเป้าหมายด้านคุณภาพ ซึ่งอาจทำให้ pull request ใหญ่ขึ้นและรีวิวช้าลงโดยการออกแบบ ในที่ที่ข้อกำหนดด้านการปฏิบัติตามกฎระเบียบจริงต้องการรีวิวอย่างละเอียด ให้เน้นความพยายามปรับปรุงที่การลดเวลารอ (มอบหมายผู้รีวิวเร็วขึ้น คัดแยกชัดขึ้น) แทนการลดความลึกจริงของการรีวิว และบันทึกข้อแลกเปลี่ยนอย่างชัดเจนถ้าการตรวจต้องเข้มต่อไปด้วยเหตุผลด้านกฎระเบียบ

## ตัวอย่าง

**องค์กรขนาดใหญ่** องค์กรวิศวกรรมของบริษัทความมั่นคงปลอดภัยไซเบอร์แห่งหนึ่งพบว่าวิศวกรระดับ principal ไม่กี่คนทำรีวิวโค้ดเสร็จกว่า 40% ของทั้งหมดในองค์กรสองร้อยคน ความไม่สมดุลที่ไม่มีใครเคยวัดโดยตรงจนกระทั่งดึงข้อมูลภาระผู้รีวิวออกมา การกระจุกตัวนี้เป็นทั้งคอขวด เพราะความพร้อมของวิศวกรเหล่านั้นเป็นเพดานของ throughput การรีวิวทั้งองค์กร และเป็นความเสี่ยงต่อภาวะหมดไฟที่ถูกชี้แยกกันโดยแบบสำรวจความผูกพัน (หัวข้อ 3.2) องค์กรนำโครงการหมุนเวียนรีวิวที่มีโครงสร้างมาใช้ควบกับเซสชันแบ่งปันความรู้แบบเจาะจง และภายในสองไตรมาส ภาระรีวิวกระจายไปสู่กลุ่มที่กว้างขึ้นมาก โดยเวลาถึงรีวิวครั้งแรกดีขึ้นเป็นผลพลอยได้โดยตรงจากคอขวดที่ลดลง

**ภาครัฐ** ทีมวิศวกรรมของหน่วยงานจัดเก็บภาษี ภายใต้แรงกดดันให้ปรับปรุงความเร็วการส่งมอบ ตั้งเป้าลดเวลาถึงรีวิวครั้งแรกลงครึ่งหนึ่ง ภายในหนึ่งไตรมาสก็ทำได้ตามเป้า แต่การตรวจสอบคุณภาพที่ตามมาพบว่า pull request แก้ข้อบกพร่องหลัง merge เพิ่มขึ้นอย่างรวดเร็ว กระจุกอยู่ในการเปลี่ยนแปลงที่ถูกอนุมัติด้วยความคิดเห็นสั้น ๆ เพียงข้อเดียว ทีมแก้ไขโดยจับคู่เป้าความเร็วกับ guardrail ด้านคุณภาพที่ชัดเจน คืออัตราการแก้ไขหลัง merge ที่ต้องทำภายในสองสัปดาห์หลังรีวิว และอบรมทีมใหม่ว่ารีวิวเชิงเนื้อหาจริงต้องทำอะไรบ้าง คืนการตรวจจริงกลับมา ขณะที่ยังรักษาความเร็วที่ดีขึ้นส่วนใหญ่ไว้ได้ ซึ่งมาจากการมอบหมายผู้รีวิวที่ดีขึ้นและ pull request ที่เล็กลง

## เหตุผลทางธุรกิจ: แรงจูงใจ ROI และ TCO

ผลตอบแทนของตัวชี้วัดรีวิวที่บริหารดีคือการส่งมอบเร็วขึ้นโดยไม่เสียคุณภาพ ซึ่งเป็นส่วนผสมที่หายาก การปรับปรุงการส่งมอบส่วนใหญ่แลกความเร็วกับความเสี่ยงที่ใดที่หนึ่ง แต่การปรับปรุงในขั้นตอนรีวิว ทั้ง pull request ที่เล็กลง การกระจายภาระที่ดีขึ้น การตอบครั้งแรกที่เร็วขึ้น ปรับปรุงทั้งสองอย่างพร้อมกันได้จริงเมื่อทำพร้อม guardrail ด้านคุณภาพที่หัวข้อนี้แนะนำ ตัวอย่างบริษัทความมั่นคงปลอดภัยไซเบอร์ข้างต้นเป็นตัวแทนที่ดี การแก้คอขวดปรับปรุงความเร็ว ขณะที่คุณภาพรีวิวพื้นฐานก็ดีขึ้นด้วยซ้ำเมื่อความเชี่ยวชาญกระจายกว้างขึ้น

ต้นทุนรวมตลอดอายุการใช้งาน (TCO) ต่ำ ตัวชี้วัดเหล่านี้ส่วนใหญ่มาจากข้อมูลของแพลตฟอร์ม version control ที่มีอยู่โดยตรง ต้องวัดเพิ่มน้อยมาก และการเปลี่ยนแปลงกระบวนการที่ตัวชี้วัดชี้ไป ทั้งการหมุนเวียนรีวิวและการส่งเสริม pull request ที่เล็กลง ส่วนใหญ่ต้องการวินัยมากกว่าการลงทุนด้านเครื่องมือ

## แอนตี้แพตเทิร์นและข้อผิดพลาด

- **ปรับเวลาถึงรีวิวครั้งแรกให้ดีโดยไม่มี guardrail ด้านคุณภาพจับคู่:** เชื้อเชิญการอนุมัติแบบประทับตราที่ทำลายจุดประสงค์ของการรีวิว
- **เพิกเฉยต่อการกระจุกตัวของภาระผู้รีวิว:** สร้างทั้งคอขวดและความเสี่ยงต่อภาวะหมดไฟที่ยังมองไม่เห็นจนกว่าจะวัด
- **มองจำนวนรอบรีวิวเป็นสมุดคะแนนรายบุคคล:** มักเป็นสัญญาณของระบบหรือการสื่อสารมากกว่าเรื่องส่วนตัว
- **ยอมรับ pull request ขนาดใหญ่ต่อเนื่องว่าเลี่ยงไม่ได้:** การเปลี่ยนแปลงใหญ่ส่วนใหญ่แยกได้ละเอียดกว่าที่ทีมคิดไว้ตอนแรก
- **ใช้ความลึกของการรีวิวเท่ากันหมดไม่ว่าความเสี่ยงของการเปลี่ยนแปลงจะเป็นอย่างไร:** เปลืองการตรวจกับการเปลี่ยนแปลงเสี่ยงต่ำ ขณะที่อาจตรวจน้อยไปกับการเปลี่ยนแปลงเสี่ยงสูง
- **วัดความเร็วรีวิวแต่ไม่เคยตรวจว่าการตรวจจริงลดลงควบคู่กันหรือไม่:** วิธีที่พบบ่อยที่สุดที่ตระกูลตัวชี้วัดนี้ถูกเล่นโดยไม่ได้ตั้งใจ

## แบบจำลองวุฒิภาวะ

- **ระดับ 1 เริ่มต้น (Initiate):** ไม่ได้ติดตามตัวชี้วัดรีวิว การกระจายภาระรีวิวและขนาด pull request มองไม่เห็น
- **ระดับ 2 พัฒนา (Develop):** มีข้อมูลความเร็วรีวิวบางส่วนจากค่าเริ่มต้นของแพลตฟอร์ม แต่ไม่มี guardrail ด้านคุณภาพและไม่มีการบริหารภาระผู้รีวิวอย่างจริงจัง
- **ระดับ 3 สร้างมาตรฐาน (Standardize):** ติดตามเวลาถึงรีวิวครั้งแรก ขนาด pull request และภาระผู้รีวิวอย่างสม่ำเสมอ พร้อม guardrail ด้านคุณภาพที่ชัดเจนจับคู่กับการปรับปรุงความเร็ว
- **ระดับ 4 บริหารจัดการ (Manage):** ปรับสมดุลภาระผู้รีวิวอย่างจริงจังผ่านการหมุนเวียนและการแบ่งปันความรู้ สืบสวนรูปแบบจำนวนรอบรีวิวในระดับกระบวนการ ไม่ใช่ระดับบุคคล
- **ระดับ 5 ประสานงาน (Orchestrate):** ตัวชี้วัดในขั้นตอนรีวิวชี้นำการลงทุนด้านกระบวนการโดยตรง และองค์กรแสดงได้ว่าทั้งความเร็วรีวิวและผลลัพธ์ด้านคุณภาพที่เกี่ยวกับรีวิวดีขึ้นพร้อมกันอย่างต่อเนื่อง

## ประเด็นเพื่อการอภิปราย

1. เวลาถึงรีวิวครั้งแรกมัธยฐานของเราตอนนี้เป็นเท่าไร และเวลานั้นหมดไปกับอะไรจริง ๆ
2. ภาระรีวิวของเรากระจุกอยู่ที่คนจำนวนน้อยหรือไม่ และความเสี่ยงคืออะไรถ้าหนึ่งในนั้นไม่อยู่
3. เราเคยปรับปรุงความเร็วรีวิวโดยแลกกับการตรวจจริง แม้โดยไม่ตั้งใจ หรือไม่
4. ขนาด pull request มัธยฐานของเราเป็นเท่าไร และการเปลี่ยนแปลงส่วนใหญ่เล็กลงได้อีกแค่ไหนอย่างสมจริง
5. เรามองจำนวนรอบรีวิวที่สูงเป็นสัญญาณของระบบหรือการตัดสินตัวบุคคล

## ข้อสรุปสำคัญ

- **เวลาถึงรีวิวครั้งแรก** มักเป็นคันโยกเดี่ยวที่ใหญ่ที่สุดในขั้นตอนรีวิว มากกว่าความยาวของบทสนทนารีวิวเอง
- **pull request ที่เล็กลง** ปรับปรุงทั้งความเร็วและความละเอียดของการรีวิวพร้อมกัน
- **ภาระผู้รีวิวที่ไม่สมดุล** พบบ่อยและมักมองไม่เห็นถ้าไม่วัดโดยตรง สร้างทั้งคอขวดและความเสี่ยงต่อภาวะหมดไฟ
- จับคู่ตัวชี้วัดความเร็วรีวิวทุกตัวกับ **guardrail ด้านคุณภาพ** ที่ชัดเจน เพื่อจับความเสี่ยงการเล่นแบบประทับตราที่ตระกูลตัวชี้วัดนี้เสี่ยงเป็นพิเศษ
- ใช้ **จำนวนรอบรีวิว** วินิจฉัยแรงเสียดทานระดับระบบ ไม่ใช่ตัดสินผู้เขียนหรือผู้รีวิวรายบุคคล

## เอกสารอ้างอิงและการอ่านเพิ่มเติม

- *Accelerate: The Science of Lean Software and DevOps*, by Nicole Forsgren, Jez Humble, and Gene Kim (code review practices and their relationship to delivery performance).
- *Modern Code Review* research by Alberto Bacchelli and Christian Bird (empirical study of code review practices at scale).
- *Peer Reviews in Software: A Practical Guide*, by Karl E. Wiegers (review process design and its trade-offs).
- *The Principles of Product Development Flow*, by Donald G. Reinertsen (batch-size reasoning applied to pull request sizing).
