# 9.1 อภิธานศัพท์

คำจำกัดความของศัพท์และคำย่อที่ใช้ตลอดทั้งเล่ม แต่ละรายการระบุหัวข้อ
ที่แนะนำศัพท์นั้นอย่างละเอียด

**Activity metric (ตัวชี้วัดกิจกรรม)** การนับการเคลื่อนไหวทางวิศวกรรม (คอมมิต, pull request,
จำนวนบรรทัดโค้ด) ซึ่งวัดปริมาณ ไม่ใช่คุณค่า ดูหัวข้อ 3.4

**Bus factor (ปัจจัยรถบัส)** จำนวนคนที่ต้องไม่อยู่ก่อน
ที่ระบบหรือความรู้ชิ้นหนึ่งจะดูแลต่อไม่ได้ Bus factor ที่เท่ากับหนึ่ง
คือความเสี่ยงร้ายแรง ดูหัวข้อ 3.5

**Change failure rate (อัตราความล้มเหลวของการเปลี่ยนแปลง)** ร้อยละของการ deploy ที่ทำให้เกิดความล้มเหลว
ในระบบ production และต้องแก้ไข เป็นหนึ่งในสี่ตัวชี้วัดของ DORA
ดูหัวข้อ 2.10

**Control chart (แผนภูมิควบคุม)** แผนภูมิที่แสดงช่วงความแปรผันปกติของตัวชี้วัด
ตามเวลา ใช้แยกการเปลี่ยนแปลงที่แท้จริงออกจากสัญญาณรบกวนทั่วไป ดู
หัวข้อ 1.6

**Cycle time** การแยกย่อย lead time ภายในเป็นขั้นตอนต่าง ๆ ได้แก่ การเขียนโค้ด
การรีวิว การทดสอบ และการ deploy ดูหัวข้อ 2.6

**CVSS (Common Vulnerability Scoring System)** มาตรฐานสำหรับให้คะแนน
ความรุนแรงของช่องโหว่ด้านความมั่นคงปลอดภัย ดูหัวข้อ 6.4

**Cyclomatic complexity (ความซับซ้อนเชิงวงจร)** การนับเส้นทางอิสระผ่านโครงสร้างการควบคุมการไหล
ของโค้ดชิ้นหนึ่ง เสนอโดย Thomas J. McCabe ในปี 1976 ดู
หัวข้อ 4.1

**DevEx (developer experience, ประสบการณ์นักพัฒนา)** กรอบคิดที่กว้างกว่าและเกี่ยวข้องกับ SPACE
จัดระเบียบรอบวงจรป้อนกลับ ภาระทางความคิด และสภาวะลื่นไหล (flow state) ดู
หัวข้อ 3.7

**Deployment frequency (ความถี่ในการ deploy)** ความถี่ที่ทีมปล่อยขึ้น production ได้สำเร็จ
เป็นหนึ่งในสี่ตัวชี้วัดของ DORA ดูหัวข้อ 2.10

**DORA metrics (ตัวชี้วัด DORA)** สี่ตัวชี้วัดจากโครงการ DevOps Research and Assessment ได้แก่
ความถี่ในการ deploy, lead time for changes, change failure rate
และเวลากู้คืนจากการ deploy ที่ล้มเหลว ดูหัวข้อ 2.10

**Error budget (งบความผิดพลาด)** ส่วนที่ขาดไปที่ยอมรับได้ระหว่างเป้าหมายระดับการให้บริการ
กับความน่าเชื่อถือ 100% ซึ่งถือเป็นทรัพยากรที่ใช้จ่ายได้ ดูหัวข้อ 6.1

**Escaped defect (ข้อบกพร่องที่หลุดรอด)** ข้อบกพร่องที่ไปถึง production และกระทบผู้ใช้จริง
ต่างจากข้อบกพร่องที่ถูกจับได้ในการรีวิวหรือการทดสอบ ดูหัวข้อ 5.1

**FinOps** แนวปฏิบัติที่นำความรับผิดชอบทางการเงินมาใช้กับ
ค่าใช้จ่ายโครงสร้างพื้นฐานคลาวด์ที่ผันแปร ดูหัวข้อ 5.4

**Flow distribution (การกระจายของ flow)** สัดส่วนของ flow item ที่เสร็จสิ้นซึ่งเป็นของ
flow item แต่ละประเภทในช่วงเวลาหนึ่ง ดูหัวข้อ 2.3

**Flow efficiency (ประสิทธิภาพของ flow)** อัตราส่วนระหว่างเวลาทำงานจริงกับเวลาที่ผ่านไปทั้งหมด
ของงานชิ้นหนึ่งที่เคลื่อนผ่านไปป์ไลน์การส่งมอบ ดูหัวข้อ 2.5

**Flow Framework** แบบจำลองเชิงการจัดการที่สร้างโดย Mik Kersten
ซึ่งมองการส่งมอบซอฟต์แวร์เป็นสายธารคุณค่า (value stream) และวัดด้วย flow item สี่ประเภท
และตัวชี้วัด flow ห้าตัว ดูหัวข้อ 2.1

**Flow item** หน่วยงานของ Flow Framework ได้แก่ ฟีเจอร์ ข้อบกพร่อง ความเสี่ยง
หรือหนี้ ซึ่งจัดประเภทตอนรับงานเข้า ดูหัวข้อ 2.2

**Flow load** จำนวน flow item ทั้งหมดที่กำลังทำอยู่หรือรออยู่ใน
สายธารคุณค่า เป็นชื่อที่ Flow Framework ใช้เรียกงานระหว่างทำ (work in process) ดู
หัวข้อ 2.4

**Flow time** เวลารวมที่ผ่านไปตั้งแต่ flow item เข้าสู่
สายธารคุณค่าจนถึงการส่งมอบ ครอบคลุมทั้งสายธารคุณค่า ไม่ใช่เฉพาะ
ฝั่งวิศวกรรม ดูหัวข้อ 2.4

**Flow velocity** จำนวน flow item ที่เสร็จในช่วงเวลาหนึ่ง
เป็นการวัด throughput ของ Flow Framework ดูหัวข้อ 2.3

**Goodhart's law (กฎของกู๊ดฮาร์ต)** หลักการที่ว่าเมื่อตัววัดกลายเป็นเป้าหมาย มันก็
เลิกเป็นตัววัดที่ดี เป็นแนวคิดหลักที่กำกับหนังสือเล่มนี้ ดู
หัวข้อ 1.2

**Guardrail metric (ตัวชี้วัด guardrail)** ตัวชี้วัดคู่ตรงข้ามที่ต้องไม่แย่ลงในขณะที่
ตัวชี้วัดที่มีแรงจูงใจดีขึ้น ออกแบบไว้เพื่อจับการเล่นแร่แปรธาตุตัวเลข ดูหัวข้อ 1.2

**Hotspot (จุดร้อน)** ไฟล์หรือโมดูลที่ทั้งถูกแก้ไขบ่อย (churn สูง)
และซับซ้อนมาก ระบุได้ด้วยการวิเคราะห์ hotspot ดูหัวข้อ 4.3

**Lead time for changes** เวลาตั้งแต่คอมมิตแรกของการเปลี่ยนแปลงโค้ด
ไปจนถึงการ deploy ขึ้น production สำเร็จ เป็นหนึ่งในสี่ตัวชี้วัดของ DORA ดู
หัวข้อ 2.10

**Little's law (กฎของลิตเติล)** การพิสูจน์ว่าจำนวนเฉลี่ยของรายการในคิวที่เสถียร
เท่ากับอัตราการมาถึงเฉลี่ยคูณกับเวลาเฉลี่ยที่รายการหนึ่งอยู่ในระบบ เมื่อใช้กับ
การส่งมอบ งานระหว่างทำเท่ากับอัตราการมาถึงคูณ cycle time ดูหัวข้อ 2.7

**Metric tree (ต้นไม้ตัวชี้วัด)** โครงสร้างที่เชื่อมตัวชี้วัดผลลัพธ์ระดับบนสุด ลงไปตามปัจจัยขับเคลื่อน
จนถึงตัวชี้วัดเชิงปฏิบัติการที่แต่ละทีมเป็นเจ้าของ ดู
หัวข้อ 1.3

**MTTA (mean time to acknowledge, เวลาเฉลี่ยในการรับทราบ)** เวลาตั้งแต่มีการแจ้งเหตุการณ์
จนถึงมีคนรับผิดชอบเข้าไปตอบสนอง ดูหัวข้อ 6.2

**MTTD (mean time to detect, เวลาเฉลี่ยในการตรวจพบ)** เวลาตั้งแต่เหตุการณ์เริ่มเกิดขึ้นจริง
จนถึงมีคนสังเกตเห็นว่าเกิดขึ้น ดูหัวข้อ 6.2

**MTTR (mean time to recovery / mean time to resolve, เวลาเฉลี่ยในการกู้คืน / แก้ไข)** เวลาที่ใช้ในการ
คืนบริการให้สมบูรณ์หลังเกิดความล้มเหลว ใช้ทั้งกับความล้มเหลวที่เกิดจากการ deploy
(หัวข้อ 2.10) และเหตุการณ์ทั่วไป (หัวข้อ 6.2)

**Mutation testing (การทดสอบแบบมิวเทชัน)** เทคนิคที่จงใจใส่ข้อผิดพลาดเล็ก ๆ
เทียม ๆ ลงในโค้ด เพื่อตรวจว่าชุดทดสอบจับได้จริงหรือไม่
เป็นส่วนเสริมของ coverage ดูหัวข้อ 4.2

**North-star metric (ตัวชี้วัดดาวเหนือ)** ตัวชี้วัดเดียวที่จับคุณค่าหลักซึ่งองค์กรส่งมอบได้ดีที่สุด
อยู่บนสุดของต้นไม้ตัวชี้วัด ดู
หัวข้อ 1.3

**Outcome telemetry** การวัดผลลัพธ์จริงอย่างต่อเนื่องผ่านเครื่องมือติดตั้ง
ไม่ใช่วัดกิจกรรมหรือผลผลิต ดูหัวข้อ 7.4

**Percent complete and accurate (%C/A)** ร้อยละของหน่วยงานที่ทีมปลายน้ำ
ประมวลผลต่อได้โดยไม่ต้องแก้ไขซ้ำ มาจากการทำแผนผังสายธารคุณค่าแบบ Lean ดั้งเดิม ดูหัวข้อ 2.8

**Process time (PT)** เวลาที่ลงมือทำงานจริงกับหน่วยงานหนึ่งหน่วย
ต่างจากเวลารอ มาจากการทำแผนผังสายธารคุณค่าแบบ Lean ดั้งเดิม ดูหัวข้อ 2.8

**Queueing theory (ทฤษฎีการจัดคิว)** การศึกษาแถวคอยทางคณิตศาสตร์ ใช้กับ
ไปป์ไลน์การส่งมอบเพื่ออธิบายว่างานระหว่างทำ อัตราการมาถึง
และอัตราการใช้งาน กำหนดเวลารอได้อย่างไร ดูหัวข้อ 2.7

**ROI (return on investment, ผลตอบแทนจากการลงทุน)** ผลตอบแทนทางการเงินของโครงการริเริ่ม
เทียบกับต้นทุน ในที่นี้สร้างจากหลักฐานต้นทุนและผลลัพธ์ที่บันทึกไว้
ไม่ใช่จากข้อสันนิษฐาน ดูหัวข้อ 5.5

**Rolled throughput yield** ตัวเลข percent complete and accurate
ของทุกขั้นในสายธารคุณค่าคูณกัน ทำให้เห็นว่างานแก้ไขซ้ำสะสมกันอย่างไรในไปป์ไลน์หลายขั้น ดูหัวข้อ 2.8

**SLI (service level indicator, ตัวบ่งชี้ระดับการให้บริการ)** สัญญาณที่วัดโดยตรงของสุขภาพ
ของบริการ เช่น latency หรืออัตราข้อผิดพลาด ดูหัวข้อ 6.1

**SLO (service level objective, วัตถุประสงค์ระดับการให้บริการ)** ช่วงเป้าหมายสำหรับ
service level indicator ดูหัวข้อ 6.1

**SPACE framework (กรอบแนวคิด SPACE)** กรอบแนวคิดห้ามิติสำหรับ
ผลิตภาพของนักพัฒนา ได้แก่ Satisfaction and well-being, Performance, Activity,
Communication and collaboration และ Efficiency and flow ดูหัวข้อ 3.1

**SRE (site reliability engineering, วิศวกรรมความน่าเชื่อถือของระบบ)** แนวปฏิบัติที่ริเริ่มที่
Google ในการนำแนวทางวิศวกรรมซอฟต์แวร์มาใช้กับการดำเนินงานและ
ความน่าเชื่อถือ ดูหัวข้อ 6.1

**Takt time** เวลาสูงสุดที่ยอมรับได้ในการทำหน่วยงานหนึ่งหน่วยให้เสร็จ
เพื่อให้ตรงกับความต้องการของลูกค้าพอดี มาจากการทำแผนผังสายธารคุณค่าแบบ Lean ดั้งเดิม
ดูหัวข้อ 2.8

**Technical debt (หนี้ทางเทคนิค)** ต้นทุนสะสมของทางลัดในอดีตภายใน codebase
เป็นอุปมาสำหรับข้อแลกเปลี่ยนที่จัดการได้ ไม่ใช่ความลับที่น่าอับอาย ดู
หัวข้อ 4.5

**TCO (total cost of ownership, ต้นทุนรวมของการเป็นเจ้าของ)** ต้นทุนทั้งหมดของโครงการริเริ่มหรือ
ระบบตลอดอายุการใช้งาน รวมการบำรุงรักษาและโครงสร้างพื้นฐานที่ต่อเนื่อง
ไม่ใช่เฉพาะต้นทุนเริ่มแรก ดูหัวข้อ 5.5

**Unit economics (เศรษฐศาสตร์ต่อหน่วย)** ต้นทุนที่แสดงเป็นต่อหน่วยคุณค่าที่ส่งมอบอย่างมีความหมาย
(ต่อลูกค้า ต่อธุรกรรม) แทนที่จะเป็นยอดรวมที่ไม่โปร่งใส ดู
หัวข้อ 5.4

**Utilization (อัตราการใช้งาน)** สัดส่วนของกำลังที่มีอยู่ของทรัพยากรซึ่งไม่ว่าง
คำนวณจากอัตราการมาถึงหารด้วยอัตราการให้บริการ เวลารอเพิ่มขึ้นอย่างฮวบฮาบ
ไม่ใช่ค่อยเป็นค่อยไป เมื่ออัตราการใช้งานเข้าใกล้กำลังเต็ม ดูหัวข้อ 2.7

**Value stream (สายธารคุณค่า)** ลำดับกิจกรรมตั้งแต่ต้นจนจบที่เปลี่ยนแนวคิดให้เป็น
คุณค่าที่ลูกค้าได้รับ เป็นหน่วยการวัดของ Flow Framework
ดูหัวข้อ 2.1

**Vanity metric (ตัวชี้วัดเพื่อความสวยงาม)** ตัวชี้วัดที่เพิ่มขึ้นเสมอ ดูน่าประทับใจ
และไม่เปลี่ยนการตัดสินใจใด ๆ ดูหัวข้อ 1.1

**Work in process (WIP, งานระหว่างทำ)** จำนวนรายการที่กำลังทำอยู่ ณ เวลาใดเวลาหนึ่ง
ในทีมหรือระบบ ดูหัวข้อ 2.5
