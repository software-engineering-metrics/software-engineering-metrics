# ตัวชี้วัดวิศวกรรมซอฟต์แวร์คืออะไร

[ตัวชี้วัดวิศวกรรมซอฟต์แวร์](https://en.wikipedia.org/wiki/Software_metric)
คือการวัดเชิงปริมาณที่ใช้ประเมิน ติดตาม และปรับปรุงคุณภาพ ประสิทธิภาพ
และผลกระทบของกระบวนการพัฒนาซอฟต์แวร์ ตัวผลิตภัณฑ์ และทีม เมื่อใช้อย่างถูกต้อง
มันทำหน้าที่เป็นเครื่องมือวินิจฉัยระดับระบบ: เผยให้เห็นคอขวดในการปฏิบัติงาน
ช่วยให้เหตุผลสนับสนุนการจัดการหนี้ทางเทคนิค และเชื่อมกิจกรรมทางวิศวกรรมเข้ากับ
ผลลัพธ์ทางธุรกิจที่จับต้องได้ แต่เมื่อใช้ผิด มันบิดเบือนพฤติกรรม ทำลายความไว้วางใจ
และให้รางวัลกับสิ่งที่ผิดอย่างตรงไปตรงมา

หนังสือเล่มนี้เกิดขึ้นเพราะทีมส่วนใหญ่หยิบตัวชี้วัดขึ้นมาก่อนจะตัดสินใจว่าตัวชี้วัดนั้น
*มีไว้เพื่ออะไร* แดชบอร์ดเต็มไปด้วยทุกอย่างที่นับง่าย ผู้บริหารเริ่มถามว่า "ตัวเลขนี้
ขึ้นหรือลง" และภายในหนึ่งไตรมาส ทีมก็เริ่มปรับแต่งตัวเลข แทนที่จะปรับแต่งผลลัพธ์
ที่ตัวเลขนั้นควรจะแทน ความล้มเหลวแบบนี้มีชื่อเรียกว่า
[กฎของกู๊ดฮาร์ต](https://en.wikipedia.org/wiki/Goodhart%27s_law) (Goodhart's law):
เมื่อตัวชี้วัดกลายเป็นเป้าหมาย มันก็เลิกเป็นตัวชี้วัดที่ดี ทุกหัวข้อในหนังสือเล่มนี้
เขียนขึ้นโดยมีกฎข้อนี้ยืนอยู่เบื้องหลัง

## กรอบแนวคิดพื้นฐานสองกรอบ

อุตสาหกรรมส่วนใหญ่เห็นพ้องกันในกรอบแนวคิดสองกรอบที่มีงานวิจัยรองรับ
สำหรับการวัดการส่งมอบงานวิศวกรรมและสุขภาพของทีม

**[ตัวชี้วัด DORA](https://dora.dev/guides/dora-metrics/)** (จากโปรแกรม
DevOps Research and Assessment) วัดปริมาณงานที่ผ่านระบบและเสถียรภาพของระบบ:
ความถี่ในการ deploy, lead time สำหรับการเปลี่ยนแปลง, อัตราความล้มเหลวของการเปลี่ยนแปลง
และเวลากู้คืนจากการ deploy ที่ล้มเหลว ส่วนที่ 2 ของหนังสือครอบคลุมทั้งสี่ตัว
ในหัวข้ออ้างอิงเฉพาะ คู่กับ Flow Framework ซึ่งใช้จัดระเบียบตัวชี้วัดการส่งมอบและ flow
ในภาพที่กว้างกว่า เพราะ DORA วัดกลไกของ pipeline ได้ดี แต่ไม่ได้บอกอะไรเลย
ว่าคุณค่าชนิดใดกำลังไหลผ่าน pipeline นั้น

**[กรอบแนวคิด SPACE](https://queue.acm.org/detail.cfm?id=3454124)**
สร้างโดยนักวิจัยจาก Microsoft, GitHub และ University of Victoria
ถ่วงดุลปริมาณงานดิบด้วยประสบการณ์ของนักพัฒนาใน 5 มิติ: ความพึงพอใจและความเป็นอยู่ที่ดี
ประสิทธิภาพ กิจกรรม การสื่อสารและการทำงานร่วมกัน และประสิทธิผลและ flow
ส่วนที่ 3 อธิบายเรื่องนี้อย่างลึกซึ้ง

นอกจากสองกรอบนี้ ทีมยังติดตามตัวชี้วัดเฉพาะจุดที่จัดกลุ่มตามโดเมน ได้แก่
ตัวชี้วัดโค้ดและคุณภาพ (ส่วนที่ 4) ตัวชี้วัดผลิตภัณฑ์และธุรกิจ (ส่วนที่ 5) และ
ตัวชี้วัดความน่าเชื่อถือ การปฏิบัติการ และความปลอดภัย (ส่วนที่ 6) ส่วนที่ 7
พูดถึงการเปลี่ยนแปลงที่กำลังเกิดขึ้นแล้ว: เครื่องมือเจนเนอเรทีฟเอไอทำให้การผลิตโค้ดดิบ
แทบไม่มีต้นทุน ซึ่งหมายความว่าตัวชี้วัดหลายตัวที่อุตสาหกรรมพึ่งพามาหนึ่งทศวรรษ
ไม่ได้มีความหมายเหมือนเดิมอีกต่อไป

## หนังสือเล่มนี้เหมาะกับใคร

กลุ่มผู้อ่านหลักคือผู้ที่เลือกว่าทีมจะวัดอะไรและทำไม: ผู้นำด้านวิศวกรรม
staff และ principal engineer ทีมแพลตฟอร์มและ DevOps และผู้จัดการโปรแกรมและผลิตภัณฑ์
ที่กำลังสร้างแดชบอร์ดหรือสกอร์การ์ดตัวชี้วัดเป็นครั้งแรก หรือกำลังซ่อมแซมอันที่เริ่มบิดเบือน
พฤติกรรม กลุ่มผู้อ่านรองคือวิศวกรทุกคนที่อยากเข้าใจว่าทำไมองค์กรของตนจึงติดตามสิ่งที่ติดตาม
และจะโต้แย้งอย่างไรเมื่อตัวชี้วัดถูกใช้ผิดวัตถุประสงค์

เริ่มที่นี่ จากนั้นอ่าน[บทนำ](introduction.md)เพื่อดูว่าหนังสือจัดโครงสร้างอย่างไร
หรือข้ามไปที่[สารบัญ](table-of-contents.md)ได้เลย

บอกว่าตัวชี้วัดที่กล่าวถึงถูกเล่นแร่แปรธาตุได้อย่างไร และปิดด้วยแบบจำลองวุฒิภาวะ
คำถามสำหรับการหารือ และเอกสารอ้างอิง คุณไม่จำเป็นต้องอ่านตั้งแต่ต้นจนจบเพื่อใช้ประโยชน์จากมัน
