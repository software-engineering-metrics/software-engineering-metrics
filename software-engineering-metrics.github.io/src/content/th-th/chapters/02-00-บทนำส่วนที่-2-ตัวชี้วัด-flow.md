# 2.0 บทนำส่วนที่ 2: ตัวชี้วัด Flow

ถ้าส่วนที่ 1 คือปรัชญาของการวัด ส่วนที่ 2 ก็คือจุดที่ปรัชญานั้นไปพบกับการส่งมอบงานจริง
ตัวชี้วัดในส่วนนี้ไม่ได้บอกแค่ว่าทีมเคลื่อนโค้ดจากไอเดียไปสู่ระบบที่ทำงานอยู่ได้เร็วและปลอดภัยเพียงใด
แต่ยังบอกด้วยว่าคุณค่าชนิดใดกำลังไหลผ่านสายพานนั้นอยู่
ส่วนนี้จัดโครงสร้างรอบ **Flow Framework** ซึ่ง Mik Kersten
สร้างขึ้นและเผยแพร่ในหนังสือ *Project to Product* ปี 2018
กรอบนี้มองการส่งมอบซอฟต์แวร์เป็นสายธารคุณค่า (value stream)
และให้ศัพท์ร่วมกับสายธารนั้น ได้แก่ flow item 4 ประเภทและตัวชี้วัด flow 5 ตัว
ซึ่งเชื่อมกิจกรรมทางวิศวกรรมเข้ากับกลยุทธ์ทางธุรกิจ
ด้วยภาษาที่ผู้มีส่วนได้ส่วนเสียฝ่ายที่ไม่ใช่เทคนิคใช้งานได้จริง

การเลือกกรอบนี้เป็นตัวจัดโครงสร้างเป็นเรื่องตั้งใจ
ตัวชี้วัด DORA ได้แก่ความถี่ในการ deploy, lead time, อัตราการเปลี่ยนแปลงที่ล้มเหลว และเวลากู้คืน
ผ่านการพิสูจน์ด้วยงานวิจัยจริง และยังเป็นหนึ่งในกรอบส่งมอบงานที่มีหลักฐานรองรับดีที่สุดเท่าที่มี
แต่มันวัดกลไกของสายพาน ไม่ได้วัดสิ่งที่ไหลอยู่ในสายพาน
ทีมหนึ่งอาจมีตัวเลข DORA ยอดเยี่ยม
ขณะที่คุณค่าที่ส่งมอบจริงค่อย ๆ เอียงไปทางงานแก้ซ้ำ
หรือห่างจากงานหนี้และงานความเสี่ยงที่ปกป้องอนาคตของระบบโดยไม่มีใครสังเกต
ส่วนนี้ครอบคลุม DORA อย่างครบถ้วน แต่ในรูปหัวข้ออ้างอิงรวมหัวข้อเดียวตอนท้าย (หัวข้อ 2.10)
เพราะคำถามที่เร่งด่วนกว่าและมักขาดหายไปในองค์กรส่วนใหญ่ไม่ใช่ "สายพานของเราเร็วแค่ไหน"
แต่คือ "สายพานของเราส่งมอบอะไรออกมาจริง ๆ"
ทุกหัวข้อในส่วนนี้ยังคงวินัยเดียวกับส่วนที่ 1 คือ ระบุตัวชี้วัด บอกว่ามันถูกเล่นแร่แปรธาตุตัวเลขอย่างไร
และจับคู่กับ guardrail ที่ดักการเล่นแร่แปรธาตุนั้น

สำหรับทีมขนาดใหญ่ ตัวชี้วัด flow คือสิ่งที่ทำให้เปรียบเทียบข้ามทีมได้โดยไม่ละสายตาจากคุณค่า
ทีมแพลตฟอร์ม ทีมมือถือ และทีมข้อมูลอาจแทบไม่มีอะไรเหมือนกันในงานประจำวัน
แต่ flow velocity และ flow distribution ที่คำนวณอย่างสม่ำเสมอ
ช่วยให้ผู้บริหารถามคำถามที่เป็นธรรมกับทั้งสามทีมได้ว่า
ทีมนี้ส่งมอบคุณค่าชนิดที่ช่วงเวลาปัจจุบันของตนต้องการจริงหรือไม่
องค์กรขนาดใหญ่และหน่วยงานภาครัฐพึ่งตัวชี้วัดในส่วนนี้เพื่อให้เหตุผลสนับสนุนการลงทุนในแพลตฟอร์ม
เปรียบเทียบผลตอบแทนของความพยายามปรับปรุงระบบที่แข่งกันเอง
และแสดงด้วยหลักฐานแทนเรื่องเล่าว่ากำลังคนด้านวิศวกรรมถูกจัดสรรตรงกับที่ผู้บริหารเชื่อ

## หัวข้อในส่วนนี้

- **2.1 Flow Framework:** ที่มาของกรอบ โมเดลสายธารคุณค่า
  และเหตุผลที่หนังสือเล่มนี้ใช้กรอบนี้ แทนที่จะใช้ DORA อย่างเดียว ในการจัดระเบียบตัวชี้วัดการส่งมอบและ flow
- **2.2 Flow item: ฟีเจอร์ ข้อบกพร่อง ความเสี่ยง และหนี้:**
  อนุกรมวิธาน 4 ประเภทของกรอบ การจัดสรรกำลังคนแบบผลรวมเป็นศูนย์
  และวิธีที่การจำแนกประเภทถูกเล่นแร่แปรธาตุตัวเลขหากทำย้อนหลัง
- **2.3 Flow velocity และ flow distribution:** ส่งมอบไปเท่าไรและเป็นคุณค่าชนิดใด ต้องอ่านคู่กันเสมอ
- **2.4 Flow time และ flow load:** กฎของลิตเติลพิสูจน์ได้อย่างไรว่า
  สายธารคุณค่าที่โหลดเกินจะช้าลงตามหลักคณิตศาสตร์ ไม่ใช่แค่น่าจะช้าลง
- **2.5 Flow efficiency และงานระหว่างทำ (work in process):**
  เหตุใดความยุ่งไม่เท่ากับความเร็ว
  และเหตุใดการจำกัดงานระหว่างทำจึงเพิ่ม throughput ได้อย่างขัดสัญชาตญาณ
- **2.6 Cycle time และองค์ประกอบ:** แยกเวลาทางวิศวกรรมของการเปลี่ยนแปลงหนึ่งรายการออกเป็นขั้นตอนย่อย
  เพื่อให้ทีมรู้แน่ว่าเวลาหายไปที่ใด
- **2.7 ทฤษฎีคิว:** คณิตศาสตร์เบื้องหลัง flow load, flow time, cycle time และงานระหว่างทำ
  และเหตุผลที่เวลารอทรัพยากรที่ใช้ร่วมกันพุ่งขึ้นอย่างรวดเร็วเมื่ออัตราการใช้งานเข้าใกล้ขีดสุด
- **2.8 ตัวชี้วัดสายธารคุณค่าแบบลีน:** ชุดเครื่องมือลีนคลาสสิก ได้แก่ lead time, process time,
  cycle time, percent complete and accurate และ takt time
  ซึ่งตัวชี้วัดเฉพาะซอฟต์แวร์ในส่วนนี้สืบทอดมา และวิธีเชื่อมศัพท์ทั้งสองชุดเข้าด้วยกัน
- **2.9 ตัวชี้วัด pull request และการรีวิวโค้ด:** ตัวชี้วัดที่อยู่ภายในขั้นตอนเดียวของสายพานการส่งมอบ
  และวิธีที่มันบิดเบือนคุณภาพการรีวิวได้หากใช้อย่างไม่ระวัง
- **2.10 กรอบตัวชี้วัด DORA:** ตัวชี้วัด DORA ทั้งสี่อย่างครบถ้วน
  ตั้งใจวางไว้ท้ายสุดเพราะมันวัดสายพาน ไม่ได้วัดคุณค่าที่ไหลอยู่ในสายพาน

## หัวข้อเหล่านี้สัมพันธ์กันอย่างไร

หัวข้อ 2.1 แนะนำ Flow Framework ในภาพรวม
หัวข้อ 2.2 ให้อนุกรมวิธานของ flow item
และหัวข้อ 2.3 กับ 2.4 ครอบคลุมตัวชี้วัด flow ทั้งห้าตัวร่วมกัน
โดย velocity คู่กับ distribution แล้วจึง time คู่กับ load
ซึ่ง load และ time ผูกโดยตรงกับกฎของลิตเติล
หัวข้อ 2.5 ถึง 2.7 ขยายเข้าไปดูกลไกเบื้องหลัง flow time และ cycle time
flow efficiency และงานระหว่างทำอธิบายว่าเหตุใดขั้นตอนทางวิศวกรรมจึงมักช้ากว่าที่ดูเหมือน
cycle time แยกส่วนวิศวกรรมนั้นออกเป็นขั้นตอนย่อย
และทฤษฎีคิวอธิบายอย่างเป็นทางการด้วยคณิตศาสตร์ที่พิสูจน์ได้
ว่าข้อกล่าวอ้างของหัวข้อก่อนหน้าทั้งหมดเรื่องโหลด เวลารอ และอัตราการใช้งานนั้นเป็นจริง
หัวข้อ 2.8 ถอยออกมาไล่ย้อนทั้งหมดไปถึงต้นกำเนิดในการทำแผนผังสายธารคุณค่าแบบลีนคลาสสิก
ซึ่งเป็นศัพท์กลางที่ตัวชี้วัดเฉพาะซอฟต์แวร์ของส่วนนี้ขยายความมา
หัวข้อ 2.9 ครอบคลุมขั้นตอนเดียวของสายพานที่ทีมส่วนใหญ่ปรับปรุงได้เร็วที่สุด
หัวข้อ 2.10 ปิดส่วนนี้ด้วยตัวชี้วัด DORA ครบถ้วน
ในฐานะชั้นอ้างอิงที่มีหลักฐานดีแต่แคบกว่า
เมื่อภาพกว้างที่เชื่อมกับธุรกิจจากหัวข้อก่อนหน้าอยู่ในสายตาแล้ว

วินัยเรื่อง guardrail ของส่วนนี้เชื่อมกลับไปยังหัวข้อ 1.2 โดยตรง
คือไม่รายงาน flow velocity โดยไม่มี flow distribution กำกับเสมอ
และตัวชี้วัดด้านความเร็วของ DORA ยังคงจับคู่กับตัวชี้วัดด้านเสถียรภาพ
เพื่อไม่ให้ทีมปรับตัวเลขความเร็วให้ดีขึ้นได้ด้วยการส่งโค้ดที่เสี่ยงกว่า
หรือคุณค่าที่หลากหลายน้อยลงโดยไม่มีใครรู้
การจับคู่นี้ไม่ใช่เรื่องบังเอิญของกรอบใดกรอบหนึ่ง
มันคือข้อคิดหลักของแต่ละกรอบ
และตัวชี้วัดด้านความน่าเชื่อถือในส่วนที่ 6 ขยายครึ่งเสถียรภาพของการจับคู่เดียวกันนี้ไปสู่การปฏิบัติการจริงบน production
เมื่อโค้ดถูกส่งมอบไปแล้ว
