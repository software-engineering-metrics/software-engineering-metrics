# 3.0 บทนำส่วนที่ 3: ประสบการณ์ของนักพัฒนาและกรอบแนวคิด SPACE

ส่วนที่ 2 วัดการส่งมอบจากภายนอก คือโค้ดเคลื่อนผ่านไปป์ไลน์ได้เร็วและปลอดภัยแค่ไหน
ส่วนนี้วัดประสบการณ์ของคนที่สร้างโค้ดนั้น และที่ต้องมีส่วนนี้ก็เพราะชุดตัวชี้วัดการส่งมอบเพียงอย่างเดียวอาจดูยอดเยี่ยม
ทั้งที่คนเบื้องหลังกำลังหมดไฟ จมอยู่กับการถูกขัดจังหวะ หรือค่อย ๆ หมดความผูกพันไปเงียบ ๆ
องค์กรที่ดูแต่ตัวชี้วัด DORA อาจปรับปรุงตัวเลขเหล่านั้นได้หนึ่งหรือสองปีด้วยการบีบทีมให้หนักขึ้น
จนกระทั่งการลาออก คุณภาพที่ล่มสลาย หรือภาวะหมดไฟลบผลที่ได้ไปทั้งหมดในคราวเดียว
ส่วนนี้คือตุ้มน้ำหนักถ่วงอีกด้านหนึ่ง

หัวใจของส่วนนี้คือ [กรอบแนวคิด SPACE](https://queue.acm.org/detail.cfm?id=3454124)
ซึ่งนักวิจัยจากไมโครซอฟต์ GitHub และมหาวิทยาลัยวิกตอเรียพัฒนาขึ้น
เพื่อแก้นิสัยของอุตสาหกรรมที่วัดผลิตภาพของนักพัฒนาด้วยตัวแทนเพียงตัวเดียวที่ถูกเล่นแร่แปรธาตุได้ง่าย เช่น จำนวนบรรทัดโค้ดหรือจำนวน commit
SPACE ครอบคลุมห้ามิติ ได้แก่ ความพึงพอใจและความเป็นอยู่ที่ดี ประสิทธิภาพ (performance) กิจกรรม การสื่อสารและการทำงานร่วมกัน และประสิทธิภาพเชิงปฏิบัติการและโฟลว์
วินัยหลักของกรอบแนวคิดนี้ ซึ่งเป็นเหตุผลที่ส่วนนี้ใช้ความเข้มงวดเท่ากับที่ส่วนที่ 2 ใช้กับตัวชี้วัดโฟลว์ของตัวเอง
คือไม่มีมิติใดมิติหนึ่งที่เชื่อถือได้ด้วยตัวเอง คุณค่าเกิดจากการมองทั้งห้ามิติไปพร้อมกัน
เพื่อไม่ให้ทีมดูดีในแกนหนึ่งโดยแอบทำลายอีกแกนหนึ่งเงียบ ๆ

สำหรับทีมขนาดใหญ่ ตัวชี้วัดประสบการณ์ของนักพัฒนาตอบคำถามที่ DORA ตอบไม่ได้
คือผลการส่งมอบนี้ยั่งยืนหรือไม่ และองค์กรรักษาคนที่สร้างมันไว้ได้หรือเปล่า
องค์กรขนาดใหญ่ที่ละเลยส่วนนี้มักรู้ต้นทุนผ่านข้อมูลการลาออกและการสัมภาษณ์ก่อนลาออก ซึ่งช้าเกินไปที่จะแก้ความเสียหาย
ส่วนหน่วยงานภาครัฐ ซึ่งมักถูกจำกัดด้วยเพดานค่าตอบแทนภาครัฐจนแข่งขันด้วยเงินเดือนล้วน ๆ ไม่ได้
ยิ่งมีเหตุผลหนักแน่นที่จะดูแลประสบการณ์ของนักพัฒนาเป็นเรื่องสำคัญอันดับแรกที่บริหารอย่างจริงจัง ไม่ใช่เรื่องที่นึกถึงทีหลัง

## หัวข้อในส่วนนี้

- **3.1 กรอบแนวคิด SPACE:** ห้ามิติรวมกัน เหตุใดไม่มีมิติใดเชื่อถือได้ลำพัง
  และวิธีสร้างชุดตัวชี้วัดที่สมดุลจริงจากห้ามิตินั้น
- **3.2 ตัวชี้วัดความพึงพอใจและความเป็นอยู่ที่ดี:** การวัดความสุขใจในงาน ความคับข้องใจ
  และความเสี่ยงของภาวะหมดไฟ ซึ่งเป็นมิติที่ telemetry ของระบบใดก็สังเกตตรง ๆ ไม่ได้
- **3.3 ตัวชี้วัดประสิทธิภาพและตัวแทนของผลลัพธ์:** มิติที่ถูกสับสนกับกิจกรรมได้ง่ายที่สุด
  และวิธีวัดการมีส่วนต่อผลลัพธ์จริงแทน
- **3.4 ตัวชี้วัดกิจกรรมและข้อจำกัด:** จำนวน commit จำนวนบรรทัดโค้ด
  และเหตุผลที่นี่คือมิติที่อันตรายที่สุดหากให้น้ำหนักมากเกินไป
- **3.5 ตัวชี้วัดการสื่อสารและการทำงานร่วมกัน:** ข้อมูลไหลระหว่างคนและทีมอย่างไรจริง ๆ
  และรูปแบบที่ดีต่อสุขภาพหน้าตาเป็นอย่างไร
- **3.6 ประสิทธิภาพและโฟลว์: การทำงานเชิงลึกและการถูกขัดจังหวะ:** การปกป้องเวลาที่ไม่ถูกขัดจังหวะซึ่งงานวิศวกรรมจริงต้องการ
  และการวัดแรงเสียดทานที่กัดกร่อนเวลานั้น
- **3.7 แบบสำรวจประสบการณ์ของนักพัฒนาและตัวชี้วัด DevEx:** วิธีทำแบบสำรวจที่ให้สัญญาณน่าเชื่อถือ
  ไม่ใช่การประกวดความนิยม และวิธีผสานกับข้อมูลเชิงวัตถุวิสัย

## หัวข้อเหล่านี้สัมพันธ์กันอย่างไร

หัวข้อ 3.1 แนะนำห้ามิติของ SPACE ไปพร้อมกัน จากนั้นหัวข้อ 3.2 ถึง 3.6 ลงลึกทีละมิติ
ตามลำดับที่นักวิจัย SPACE นำเสนอ หัวข้อ 3.7 ปิดส่วนนี้ด้วยกลไกเชิงปฏิบัติของการออกแบบแบบสำรวจ
เพราะความพึงพอใจ ประสิทธิภาพ และการทำงานร่วมกันต่างพึ่งข้อมูลที่รายงานด้วยตนเองอยู่บางส่วน
(ความแตกต่างระหว่างการวัดด้วย instrumentation กับการรายงานด้วยตนเองในหัวข้อ 1.5 เกี่ยวข้องโดยตรงตลอดทั้งส่วนนี้)
และแบบสำรวจที่ออกแบบไม่ดีจะบ่อนทำลายทุกหัวข้อก่อนหน้า

วินัยหลักของส่วนนี้ คือความสมดุลระหว่างมิติแทนที่จะเก่งมิติเดียว
เป็นตัวอย่างที่ชัดที่สุดของหนังสือเล่มนี้ในการใช้หลักการผลลัพธ์เหนือผลผลิตของหัวข้อ 1.3 กับผู้คน ไม่ใช่กับไปป์ไลน์การส่งมอบ
กิจกรรม (หัวข้อ 3.4) เป็นมิติของ SPACE ที่คล้ายตัวชี้วัดผลผลิตล้วน ๆ มากที่สุด และส่วนนี้ปฏิบัติต่อมันตามนั้น
คือมีประโยชน์ในฐานะข้อมูลนำเข้าหนึ่งในห้า แต่อันตรายเมื่อเป็นสัญญาณเดี่ยว
เมื่ออ่านคู่กับส่วนที่ 2 ส่วนนี้เติมภาพที่ DORA เพียงลำพังให้ไม่ได้ให้สมบูรณ์
คือไม่ใช่แค่ว่าซอฟต์แวร์ส่งมอบได้เร็วและปลอดภัยหรือไม่ แต่คนที่ส่งมอบรักษาจังหวะนั้นไว้ได้ต่อเนื่องหรือเปล่า
