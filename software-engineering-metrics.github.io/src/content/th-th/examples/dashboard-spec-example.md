# ตัวอย่าง: ข้อกำหนดแดชบอร์ดสำหรับแดชบอร์ดตัวชี้วัดการส่งมอบ

ตัวอย่างข้อกำหนดแดชบอร์ดที่ใช้งานได้จริง ตามแนวทางของ
[หัวข้อ 8.1 การออกแบบแดชบอร์ดตัวชี้วัดวิศวกรรม](../chapters/08-01-การออกแบบแดชบอร์ดตัวชี้วัดวิศวกรรม.md)
จุดสำคัญคือรูปทรง: กลุ่มผู้ชมที่มีชื่อ จำนวนช่องที่น้อย มาตรฐานการแสดงภาพที่ซื่อตรง
และรอบการรีเฟรชที่ระบุไว้

## กลุ่มผู้ชม

ผู้นำฝ่ายวิศวกรรมและทีมแพลตฟอร์ม ทบทวนในการประชุมทบทวนการส่งมอบทุกสองสัปดาห์
ไม่ได้มีไว้เพื่อประเมินผลงานรายบุคคล

## ช่อง (ตามลำดับที่แสดง)

1. **ความถี่ในการ deploy** ย้อนหลัง 4 สัปดาห์ แยกตามทีม แผนภูมิเส้น
   แบ่งช่วงรายสัปดาห์ แกนเริ่มที่ศูนย์
2. **Lead time สำหรับการเปลี่ยนแปลง** ค่ามัธยฐานและเปอร์เซ็นไทล์ที่ 90 ย้อนหลัง 4 สัปดาห์
   แผนภูมิแท่งที่แสดงทั้งสองชุด ไม่ใช่แค่ค่ามัธยฐาน
3. **อัตราความล้มเหลวของการเปลี่ยนแปลง** ย้อนหลัง 4 สัปดาห์ โดยมีลิงก์จากช่องไปยัง
   คำนิยามของ "ความล้มเหลว" ที่ทีมตกลงกัน
4. **เวลากู้คืนจากการ deploy ที่ล้มเหลว** ค่ามัธยฐาน ย้อนหลัง 4 สัปดาห์
5. **งบประมาณข้อผิดพลาดที่เหลือ** ไตรมาสปัจจุบัน แยกตามบริการ เป็นเปอร์เซ็นต์

## กฎการแสดงภาพ

- แผนภูมิแนวโน้มทุกอันแสดงจุดข้อมูลอย่างน้อยแปดจุด ไม่ใช่ภาพนิ่งเพียงภาพเดียว
- แกนเริ่มที่ศูนย์ เว้นแต่มีข้อยกเว้นที่บันทึกไว้บนช่อง
- การ deploy เหตุการณ์ผิดปกติ และวันหยุด มีหมายเหตุกำกับบนเส้นเวลา เพื่อให้ผู้อ่าน
  แยกการเปลี่ยนแปลงจริงออกจากสัญญาณรบกวนได้
- ไม่ใช้แกนคู่ ไม่ใช้เอฟเฟกต์ 3 มิติ ไม่เลือกช่วงวันที่เฉพาะที่เข้าข้างตัวเอง

## รอบการรีเฟรช

ช่องที่ได้ข้อมูลจาก pipeline (ความถี่ในการ deploy, lead time) รีเฟรชทุกชั่วโมง
ช่องที่ได้ข้อมูลจากเหตุการณ์ผิดปกติ (อัตราความล้มเหลวของการเปลี่ยนแปลง, เวลากู้คืน) รีเฟรชเมื่อปิดโพสต์มอร์ตัม
แดชบอร์ดแสดงเวลารีเฟรชครั้งล่าสุดของตัวเอง

## สิ่งที่แดชบอร์ดนี้ตั้งใจละเว้น

จำนวน commit รายบุคคล จำนวน pull request รายบุคคล และจำนวนบรรทัดของโค้ด
เหล่านี้เป็นตัวชี้วัดกิจกรรมที่มีประวัติถูกเล่นแร่แปรธาตุอย่างชัดเจน
และวัดความพยายามมากกว่าผลลัพธ์ (หัวข้อ 3.4)
